# 测试用例与指标说明

本目录包含 MemCache 和 Mooncake 两条接入方案。阅读结果时，先确认测试对象、模型、源码版本、设备和请求长度，再比较延迟或吞吐。
MemCache 的 vLLM 0.24 实测条件与结果见[迁移报告](memcache/docs/vllm_024_migration_results.md)，
运行方法见[部署说明](memcache/docs/vllm_deployment_flow.md)。Mooncake 的记录属于另一套历史环境，
其测试脚本的当前状态见[Mooncake 说明](mooncake/README.md)。

## 先区分测试测量了什么

| 测试类型 | 实际执行的操作 | 结果回答的问题 |
|---|---|---|
| 存储 API 基准 | 直接调用读写接口，搬运指定大小的缓冲区 | 接口延迟、成功率和有效传输吞吐是多少？ |
| MemCache 工作负载测试 | 模拟 prefill/decode 的 KV 写入和读取，不运行模型 | 不同数据量、并发和存储容量下，缓存读写是否正常？ |
| vLLM 集成测试 | 启动模型服务，通过 HTTP 发送推理请求 | 接入缓存后的首 token 延迟、命中来源和生成结果是否符合预期？ |
| 吞吐测试 | 按给定速率或并发数发送多条请求 | 一段时间内完成多少请求、生成多少 token？ |
| 工具与单元测试 | 检查源码准备、版本核对、HTTP 处理及底层函数 | 部署工具和函数的分支行为是否正确？ |

存储操作的耗时与模型请求的 TTFT 是不同的测量对象。工作负载测试即使在函数名中使用 `ttft`，
也只测模拟 KV 读写；模型集成测试还包含调度、计算和响应传输。

## 请求、缓存与并行配置

- **token**：模型处理文本的基本单位。输入 token 数决定需要处理的上下文长度，输出 token 数决定生成长度。
- **prefill（输入预处理）**：模型处理输入 token，生成后续计算需要的缓存。
- **decode（逐 token 生成）**：使用已有缓存逐步生成新 token。这里的 decode 指推理阶段，不是文本编码转换。
- **KV cache**：保存注意力计算产生的 key/value，重复输入前缀时可以复用。混合注意力模型还需要恢复对应的 Mamba 状态。
- **prefix cache（前缀缓存）**：按输入前缀查找可复用的缓存块。可复用长度受块大小、Mamba 状态保存位置等因素影响。
- **本地命中**：复用当前 vLLM 实例持有的缓存块；**外部命中**：通过 connector 从 MemCache 或 Mooncake 读取缓存。
- **TP（张量并行）**：将模型计算分到多个 worker。TP=1 使用一个设备，TP=2 使用两个设备；每个 worker 的编号称为 rank。
  在本文的 310P Duo 配置中，一张物理卡有两个 die，设备 4、5 是同卡的一组。两个设备不等于两张物理卡。
- **HBM / DRAM**：分别指设备内存和主机内存。配置中的容量是缓存池大小，还需要给模型权重、vLLM 缓存和临时计算留出空间。
- **SDMA**：设备的数据搬运机制。协议名 `device_sdma` 描述搬运方式，具体耗时还受数据量、接口调用和同步影响。

## MemCache 的四项 vLLM 集成测试

当前主测试文件是 [`vllm_integration_test.py`](memcache/cases/python/memcache/integration/vllm_integration_test.py)。
每种模型和 TP 配置执行下面四项。本轮两个模型、TP=1/TP=2，共计 `2 × 2 × 4 = 16` 项。
TTFT 采样使用 4096 输入 token、生成 1 token、1 次预热和 10 次正式测量；完整启动参数以迁移报告为准。

### 全 miss 基准：比较未命中时接入缓存的影响

**miss（未命中）**表示本次没有可复用的缓存前缀。测试分别启动不使用 MemCache 和使用 MemCache 的服务，
向两者发送同一组互不重复的输入，并使用一致的模型和推理参数。
每次请求结束后重置本地前缀缓存，减少前一请求对下一请求的影响。

这项测试回答：请求无法从缓存节省计算时，接入 MemCache 会使 TTFT 改变多少？
未命中请求仍要处理完整输入，并会经过 connector 查询、缓存管理和保存调度；不同操作可能异步执行。
结果记录两组 P50 及相对差值，不能用这组差值代替命中场景的收益。

### 50% 命中：同一批请求中有命中，也有未命中

先发送 5 个输入，让它们的缓存写入 MemCache，再将这 5 个重复输入与 5 个新输入混合、打乱顺序后发送。
测试检查每个请求的本地和外部命中计数，将延迟分别归入命中组、未命中组，并统计整批请求。

这里的 **50% 按请求数计算**：10 个测量请求中，5 个应发生外部命中。
每个命中请求实际复用了多少 token，由外部命中计数记录。由于缓存块和 Mamba 状态需要对齐，
重复 4096-token 输入时也可能只复用其可用前缀，仍需计算末尾一部分。

这项测试用于观察混合流量下两类请求的耗时及整批请求的统计值。
整批 P50 要把所有原始样本一起排序，不能将命中 P50 和未命中 P50 简单取平均。

### 配对 miss/hit：比较同一个输入写入前后的耗时

在使用 MemCache 的同一个服务中，为每个新输入执行一组操作：先发送一次，检查没有外部命中；
等待保存后再次发送相同输入，检查发生外部命中。共测量 10 组，分别统计第一次和第二次请求。

测试名称中的“100% 命中”指第二次请求这一组都应发生外部命中。每组第一次请求仍是 miss。
这里的配对 miss 来自启用 MemCache 的服务，与全 miss 基准中不启用 MemCache 的基线属于不同样本组。
该用例还用文本输入比较写入前后的输出 token，检查读取缓存后的生成结果。

### 缓存来源与生成正确性：确认读取了哪份缓存

先用不接入 MemCache 的服务生成短输入 A 和较长输入 B 的参考 token，并检查基线重复生成的一致性。
然后在 MemCache 服务中保存 A、B，构造以下三种请求：

| 场景 | 本地命中计数增量 | 外部命中计数增量 | 检查目的 |
|---|---:|---:|---|
| 清理本地缓存后重发 A | 0 | 大于 0 | 确认从 MemCache 恢复数据 |
| 保留本地缓存再次发送 A | 大于 0 | 0 | 确认本地前缀复用 |
| 保留 A 的本地缓存后发送共享前缀的 B | 大于 0 | 大于 0 | 确认本地缓存与外部缓存可以共同使用 |

每一步都将生成 token 与独立参考结果比较，文本检查最多生成 8 token。
“响应很快”本身不用于判断命中；来源由指标增量确认，正确性由输出 token 确认。

### 为什么测量时还要保留本地 prefix cache

当前 vLLM 0.24 的混合注意力测试使用 Mamba `align` 模式，因此启动时开启本地 prefix cache。
三项延迟用例在请求完成后调用 `POST /reset_prefix_cache?reset_external=false`，只重置本地缓存，保留 MemCache 数据。
重置和命中指标查询位于 TTFT 计时之外。测试同时检查 HTTP 响应及引擎新增的成功重置日志。
缓存来源正确性用例则按上述步骤有意保留本地缓存。

## 性能表中的指标怎么读

**TTFT（Time To First Token）**是从发送请求到收到第一个实际生成 token 的时间，单位通常为 ms。
它包括请求传输、调度、输入处理或缓存恢复，以及首 token 生成和返回。
它与整个回答生成完毕的时间不同。**平均输出 token 间隔**描述生成开始后相邻 token 的耗时，
需要多 token 的流式测量。ITL（Inter-Token Latency）记录相邻 token 的到达间隔；
TPOT（Time Per Output Token）通常用首 token 之后的生成时间除以其余输出 token 数。
生成 1 token 的 TTFT 测试不计算这两个指标。完整请求耗时则计到整个响应结束，
而端到端 TTFT 的终点是首个 token；“端到端”描述计时边界，仍需看具体终点。

**P50**是第 50 百分位数，也就是中位数。将耗时从小到大排序后，它位于样本中间。
例如 `[100, 120, 140, 1000] ms` 的 P50 为 130 ms，平均值为 340 ms。
MemCache 主集成脚本使用线性插值计算百分位数。P90/P99 分别描述较慢的 10%/1% 样本附近的耗时；
只有 10 个测量样本时，P99 接近最大值，需连同样本数一起阅读。

| 报告列 | 样本来自哪里 | 用途 |
|---|---|---|
| 基线 P50 | 不使用 MemCache、无可复用前缀的请求 | 作为接入缓存前的参考 |
| MemCache miss P50 | 全 miss 基准中启用 MemCache 的请求 | 观察未命中时的耗时变化 |
| 相对差值 | `(MemCache miss P50 − 基线 P50) / 基线 P50 × 100%` | 正值表示耗时增加，负值表示耗时减少 |
| 50% 场景 hit P50 / miss P50 | 混合请求中分别确认命中和未命中的样本 | 分开观察两类请求 |
| 配对 miss P50 | 配对测试中每个输入第一次发送的请求 | 启用 MemCache 后的未命中参考 |
| 配对 hit P50 | 同一测试中每个输入第二次发送的请求 | 观察从外部缓存读取后的耗时 |
| hit/miss 比值 | `配对 hit P50 / 配对 miss P50` | 越小表示命中请求相对更快；10% 表示耗时约为 miss 的十分之一 |

若基线为 100 ms、MemCache miss 为 105 ms，相对差值为 +5%。
若配对 miss 为 100 ms、配对 hit 为 10 ms，耗时减少 90%，加速倍数为 10 倍。
这些数值描述不同比较对象，应与对应列一起引用。

`avg` 表示算术平均值，`min/max` 表示最小/最大样本。`pp` 表示百分点：
例如 6.14% 到 10.95% 相差 4.81 个百分点。MB/s 使用十进制字节单位，
MiB/s 使用 `1 MiB = 1024 × 1024 bytes`，比较带宽前要统一单位。
工作负载中的 R² 表示输入数据量与耗时的线性拟合程度，越接近 1，所测样本越符合拟合直线。

**吞吐**按一段时间内完成的工作量计算：req/s 表示每秒请求数，output tok/s 表示每秒生成的输出 token 数。
input tok/s 和 total tok/s 分别计入输入及输入加输出。读取吞吐结果时还要看请求速率、并发、长度和失败数。
`simple_throughput_bench.py` 使用非流式响应，字段 `latency_ms` 和 `ttft_ms` 都从发请求计到完整响应读完；
该脚本的这个 `ttft_ms` 字段按完整请求耗时理解，与主集成脚本的流式 TTFT 分开阅读。
失败请求以零耗时、零 token 的条目加入结果，因此 `request_throughput` 计入失败条目，延迟统计也会受到影响；
读取这些字段时应同时核对日志中的 `[ERROR] request` 和请求返回情况。该脚本不提供逐 token 间隔。

## Mooncake 的测试场景

下表说明 Mooncake 历史方案中各场景的目的。当前仓库没有提交 README 引用的三个 `tests/demo_*.py`，
因此这些说明来自已有方案记录；脚本缺失情况和历史版本见 Mooncake README。

| 场景 | 做法与目的 |
|---|---|
| `single_write` / `single_read` | 两进程之间写入或读取单个缓冲区，比较发送和接收数据 |
| `batch_write` / `batch_read` | 一次传输多个缓冲区，检查每份数据 |
| `async_write` / `async_read` | 提交异步任务，再查询完成状态，确认完成后检查数据 |
| `large_buffer` | 增大缓冲区，检查较大数据量的传输 |
| `multi_segment` | 注册多个独立内存段，再分别传输，检查地址选择 |
| `probe` | 检查两端连通性，再执行传输 |
| `register_unregister` | 注册、取消注册及批量注册，检查内存注册的生命周期 |
| `vllm_baseline` | 不接入外部 KV 传输，检查模型能否加载和生成结果 |
| `vllm_kvboth_mf` | 同一个实例既发送又接收 KV，检查 connector 初始化、注册及推理 |
| `vllm_pd_disagg_mf` | 将 prefill 和 decode 放在两个服务，通过代理路由，检查 KV 交接后的生成 |
| `vllm_kv_offload_mf` | 用 Mooncake Store 保存 KV，再读取重复前缀，检查存储接入 |
| `ttft_baseline` | 不使用外部缓存，测互不重复输入的首 token 延迟 |
| `ttft_store_hit` | 先保存输入，再清本地缓存、重发相同输入，比较未命中与外部命中 |
| `ttft_offload` | 保存一段较长前缀，再发送此前缀加新后缀，观察复用前缀后仍计算后缀的耗时 |

“完全重复输入”描述输入重叠程度。实际复用 token 数还要看缓存块边界、保存状态和命中指标。
外部命中后的端到端 TTFT 仍包含查询、加载、调度及首 token 计算，不能作为单独的内存读取耗时。

## 常见术语

| 原词 | 本文采用的说法和含义 |
|---|---|
| warmup | 预热：正式统计前先执行若干请求，预热样本不计入结果 |
| pre-populate | 预先写入缓存：先执行请求并保存结果，供后续命中测试读取 |
| eviction | 缓存迁移或淘汰：容量不足时向下一存储介质搬迁，或回收条目 |
| rewarm | 从 DRAM 恢复到 HBM，以便后续复用 |
| offload | 将当前 vLLM 实例的 KV 保存到外部缓存，供以后加载 |
| watermark | 容量使用比例：如使用量达到配置比例时触发迁移 |
| key / blob | 缓存条目标识 / 实际存储的数据对象 |
| block | 缓存管理的一块数据，对应一定数量的 token；按缓存配置分配 |
| L2G / G2L | 本地缓冲区写到 MemCache / 从 MemCache 读回本地缓冲区 |
| fallback | 原路径失败后改用另一条实现，具体采用哪条路径需看日志 |
| Marker | 用于确认组件初始化或调用路径的日志标记 |

## 为什么部分 IPv6 单元用例仍会等待

IPv6 是否跳过由各用例自行判断。`smem_trans_create_success_ipv6` 等成功通信用例会检查
`IsIpv6LoopbackAvailable()`，不满足时跳过；当前的 `smem_trans_register_mem_failed_invalid_param_ipv6`
和 `smem_trans_batch_write_failed_invalid_param_ipv6` 没有同样的跳过判断，会先尝试建立配置存储连接。
本次日志中它们各等待约 127 秒后通过，成功通信类 IPv6 用例则跳过。这是用例实现的差别。
