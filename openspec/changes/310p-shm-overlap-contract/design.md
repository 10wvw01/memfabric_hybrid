# 设计文档：知识沉淀的归置结构

## Context

本变更是文档/规范工作，"实现"的对象是知识的归置结构，不是代码。三个输入约束（见
proposal.md - Why）：

1. 产品代码注释大量引用三份根目录过程文档的**文件路径与章节锚点**（如
   `hybm_overlap_prep.h` 引用"310p-aicore-aicpu-开发进展.md D4/A.3"）——移动文件
   会引发一串产品代码注释修改，风险不对等；
2. 五类知识的生命周期不同（平台配方 10 年 / 设计决策架构存续期 / 进展记录冻结 /
   踩坑记录流程期 / TODO 待办），混排是当前可读性问题的根因；
3. OpenSpec 目录（`openspec/specs/`）为空且 schema 为 spec-driven——行为契约有
   天然的归置容器，且归档后自动成为可回归验证的主 spec。

## Goals / Non-Goals

**Goals:**

- 每类知识有唯一、可预期的去处；新读者按角色（写 kernel/排查/运维）能直接定位
- 过程文档冻结后仍可读（历史价值保留），但明确声明"技术内容以档案为准"
- PR 清理 checklist 与工作法沉淀为可复用流程资产

**Non-Goals:**

- 不改写三份过程文档的正文内容（仅修复 ec1ee588 的四处残留 + 加状态指针头）
- 不为 VMM 池化（2-rank）能力另立 spec（摊大一期，见 proposal Impact）
- 不迁移过程文档到 docs/（引用链成本，见 Context-1）

## Decisions

### D1：知识五分法与去处映射

| 知识类型 | 生命周期 | 去处 |
|---|---|---|
| 平台机制配方（SQE/cache/通知链/状态机） | 10 年 | `docs/310p/机制档案.md` |
| 部署链规则与三堵墙 | 10 年 | `docs/310p/部署档案.md` |
| 平台实机事实（F1-F20/定论表/工具链） | 10 年 | `docs/310p/平台事实.md` |
| 行为契约（开关/冒烟/API 语义/布局锁） | 架构存续期 | spec delta → 归档进 `specs/310p-shm-overlap/` |
| 进展记录、设计决策 D1-D10 原文、TODO | 历史/待办 | 三份过程文档原地冻结 |

**备选**：全部进 OpenSpec specs——被否，specs 是行为契约不是技术手册；全部进 docs/
——被否，行为契约需要 SHALL/MUST 的可验证形态与变更门控。

### D2：档案为"提炼副本"而非"剪切搬迁"

`docs/310p/` 从过程文档**复制并重组**知识，过程文档不删内容、原地冻结加指针头。
理由：git blame 历史与外部引用（wiki/issue 可能链到原文件）不断链；档案可按读者
角色重新组织（过程文档按时间线组织，不可读性是结构性的）。
**代价**：短期内同一知识存在两份，靠指针头声明"档案为准"消歧。

### D3：docs/310p/ 采用中文文件名

跟随 `docs/架构概览.md` 先例（内容文档中文名、接口文档英文名的隐性惯例）。

### D4：残留修复与档案建设分离提交

四处残留修复（WP1）是纠错，档案建设（WP2/WP3）是新增——不同逻辑单元分开提交，
残留修复可独立 review 与回退。

### D5：工作法文档放 `docs/` 全局位置而非 `docs/310p/`

"探测→计划→关卡→产品化→验收→清理"是平台适配的通用方法（VMM 池化与协同迁移两次
实践同构），不限于 310P；踩坑记录中 bash/CMake/ASAN 等条目也是全仓库通用的。

## Risks / Trade-offs

- [档案与原文短期双份，可能漂移] → 指针头声明档案为准；过程文档冻结（状态头
  明示"不再更新"）；后续新增知识直接写档案
- [spec 捕获的是"已验收现状"，未来行为演进需同步改 spec] → 这是 spec-driven 的
  预期机制：行为变更走新 change 的 delta，归档时合入主 spec
- [中文文件名在部分工具链（sphinx/CI artifact）可能有兼容坑] → 仓库已有
  `docs/架构概览.md` 先例且未报问题；若未来 doc 工具链收严，rename 成本可控
- [kernel 头注释修正动产品代码文件] → 仅注释一行、零行为变化，与 ec1ee588 中
  "4 处源码注释引用同步修订"同性质

## Migration Plan

1. WP1 修复残留（独立可回退）→ 2. WP2 建档 + 指针头 → 3. WP3 工作法 →
4. 归档 change（spec delta 合入 `specs/310p-shm-overlap/`）。全流程无部署动作，
   回滚 = git revert 对应提交。
