# 10｜性能分析与下一步优化方法论：先建立模型，再动代码

> 本章位置：主线第五幕。目标是学会判断“下一刀砍哪里”，而不是看到某个阶段慢就凭直觉优化。

---

## 1. 优化前先固定 baseline

每轮实验至少记录：

```text
commit / CANN / firmware
模型与量化配置
TP / speculative 配置
q / small-M / Graph 开关
输入输出长度分布
并发
TTFT / ITL / throughput
正确性 reference
```

没有固定 baseline，就无法判断收益来自代码还是环境变化。

---

## 2. MM+AR 的简单时间模型

可以先粗略写成：

```text
T_stock ≈ T_MM + T_AR + T_launch

T_fused ≈ T_fixed
        + max(可重叠的 MM, 可重叠的 SDMA)
        + T_exposed_wait
        + T_add
        + T_tail
```

融合收益真正来自：

```text
减少固定启动成本
+ 把部分通信藏到 MM 后面
```

不是减少 MM FLOPs。

---

## 3. 第一优先级：拿到真实 M histogram

不要只测：

```text
M=256/512/1024
```

应该从实际 Qwen3.6 + DFlash 服务采集：

```text
M=1~16 占多少？
17~64 占多少？
65~256 占多少？
>256 占多少？
```

如果 80% 请求落在 small-M，优化大 M path 再漂亮也可能没有端到端价值。

---

## 4. q=1/2/4 到底影响什么

```text
batch_m = 256*q
```

q 小：

```text
更早 signal
更细粒度 overlap
更多 batch/同步开销
```

q 大：

```text
更少 batch
同步固定成本更低
但首批通信启动更晚
```

所以 q 没有理论固定最优值。

实验必须同时看：

```text
kernel 时间
SDMA overlap
wait bubble
端到端 ITL
```

---

## 5. lookahead 应该怎样判断

如果当前 lookahead=1：

```text
P0 P1 W0/A0 P2 W1/A1 ...
```

可比较：

```text
0：最保守
1：当前
2+：更深 pipeline
```

但更深不一定更快，可能造成：

```text
arena 压力
queue 反压
更长 live range
异常恢复更复杂
```

只有 profiler 显示通信暴露且队列还有余量时才值得加深。

---

## 6. small-M 优化怎样找 break-even

应扫：

```text
M=1,2,4,8,16,32,64,128,256
```

比较：

```text
stock
M-split fused
N-split fused
```

找到交点，再决定 threshold。

不要把某台机器一次测到的 53μs/150μs 当永久常数。

---

## 7. “边搬边规约”什么时候值得做

更细粒度想法：

```text
MM tile 完成
 -> 立即搬
 -> peer 到达
 -> 立即 add
```

理论上能进一步缩短尾巴。

但前提是 MemFabric public API 能表达：

```text
sub-batch completion
独立 signal/wait
地址与长度
足够低的 per-chunk 固定开销
```

如果 chunk 太小，signal/wait 固定成本可能反而压过收益。

所以先测当前 batch 内部：

```text
MM 时间
SDMA 时间
尾部暴露时间
```

只有尾部确实大，才值得把协议进一步切细。

---

## 8. Add 要不要融进 MM

直觉上：

```text
少一个 kernel = 更快
```

但如果为了等 peer 数据，让 MM 核停下来：

```text
原本可重叠的通信/计算
变成串行依赖
```

可能更慢。

更合理的问题不是“能不能融”，而是：

> peer 数据到达时间与 AI Core 空闲窗口是否对齐？

用 timeline 回答。

---

## 9. TP>2 为什么必须重新设计

TP=2 时：

```text
Y = Y0 + Y1
```

两个 rank 互换 partial 后本地 add 即可。

TP=4：

```text
Y = Y0+Y1+Y2+Y3
```

这已经需要真正的 collective algorithm：

```text
ring
reduce-scatter/allgather
树形 reduction
多 peer direct exchange
```

所以不要把 world_size 从 2 改成 4 就称为支持 TP4。

---

## 10. 低精度通信怎样做收益上限判断

假设 FP16 transport 占明显带宽：

```text
FP16 -> INT8/BF16/其它压缩
```

可能减少通信字节，但会引入：

```text
quant/dequant
scale metadata
数值误差
新 kernel
```

先估算：

```text
最多能省多少 SDMA 暴露时间？
```

如果通信已经被 MM 全部隐藏，压缩几乎没有端到端上限，就不应优先做。

---

## 11. 设计审视：性能优化的“更好演进”是什么

最成熟的方向不是不断手调常数，而是：

```text
静态 q/threshold
  ↓
offline autotune
  ↓
按 shape 建 performance table
  ↓
runtime policy selection
  ↓
结合 Scheduler workload 的自适应策略
```

机制保持稳定：

```text
correctness protocol
```

策略逐步自动化：

```text
q / split / threshold / lookahead
```

这比把某组实测常数永久写死更可持续。

---

## 12. 实验卡模板

每次优化建议写：

```text
假设：我认为 X 是主要暴露时间
证据：profiler 中 X 占 xx
改动：只改 Y
预测：M<64 时下降 xx，M>256 不变
正确性：reference / repeated / graph
结果：端到端与 microbench
结论：保留 / 回退 / 下一实验
```

真正的优化能力，就是不断缩短“假设 -> 证据 -> 实验 -> 推翻/保留”的循环。
