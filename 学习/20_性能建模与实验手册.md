# 20｜性能建模与实验手册：怎样用数据判断当前方案是不是还值得保留

> 本章位置：主线第五幕。10 讲方法，这一章把方法变成可以直接上 310P 服务器执行的实验框架。

---

## 1. 先定义四类问题

所有实验先归类：

```text
A. Correctness：结果对不对？
B. Mechanism：协议/Graph/生命周期是否稳定？
C. Micro Performance：单算子快不快？
D. End-to-End：Qwen3.6 服务真正变快了吗？
```

不要拿 microbench 代替端到端，也不要端到端一慢就直接认定 kernel 慢。

---

## 2. Correctness 最小矩阵

至少覆盖边界：

```text
M = 1
M = 15/16/17
M = 31/32/33
M = 63/64/65
M = 127/128/129
M = 255/256/257
M = 511/512/513
```

每个 M 比较：

```text
stock local MM + reference TP SUM
vs
fused MM+AR
```

检查：

```text
shape
dtype
max abs/rel error
repeated consistency
rank0/rank1 一致性
```

---

## 3. q sweep

对 q：

```text
1,2,4
```

扫 M：

```text
256
512
768
1024
2048
4096+
```

记录：

```text
producer time
signal/wait time
SDMA duration
add time
exposed communication
whole op latency
```

最终不是选“micro 最快的 q”，而是结合真实 M 分布算加权收益。

---

## 4. small-M sweep

重点：

```text
M=1..256
```

至少比较：

```text
stock
normal fused M-split
small fused N-split
```

输出一张 break-even 曲线：

```text
latency(us)
  ^
  | \ normal
  |  \____
  |      \____
  |  small ---\___
  +----------------> M
          ^ threshold
```

threshold 应来自交点和真实 workload 权重。

---

## 5. profiler 时间线应该看什么

理想时间线不是“每个 kernel 都短”，而是关键资源重叠：

```text
AI Core: [MM0][MM1][MM2][MM3]
SDMA:         [TX0][TX1][TX2]
Vector/Add:        [A0][A1][A2]
```

重点问：

```text
TX0 是否在 MM1 期间发生？
wait 是否形成大片 bubble？
Add 是否挡住下一 producer？
quiet 是否只在 wave 尾？
core0 ready polling 是否拖尾？
```

---

## 6. 固定开销拆分实验

可以逐层禁用/替换，估固定成本：

```text
MM only
MM + ready
MM + signal no useful transfer
transport only
wait + add
full fused
```

目的不是做生产配置，而是建立：

```text
T_fixed = T_runtime + T_control + T_launch + ...
```

知道小 M 为什么慢。

---

## 7. Graph 实验必须分三类

### capture 首次

关注：初始化是否意外进入 capture。

### replay steady-state

关注真正服务态延迟。

### eager <-> Graph 切换

验证 generation/control state 不串。

测试：

```text
eager N 次
Graph replay N 次
再 eager N 次
不同 shape/graph bucket 交错
```

这比只跑一个固定 Graph 1000 次更容易发现生命周期 bug。

---

## 8. repeated / soak 测什么

1000 次重复主要抓：

```text
generation reuse
arena reuse
race
偶现错数
协议状态漂移
```

更长 soak 还要看：

```text
内存增长
weight cache 上限
异常恢复
worker shutdown
```

---

## 9. Qwen 端到端实验

固定至少三类 workload：

### Prefill-heavy

```text
长 prompt，短 output
```

### Decode-heavy

```text
短/中 prompt，长 output
```

### 真实混合并发

```text
不同 prompt/output 长度
并发 1/4/10/更高
```

分别测：

```text
TTFT
ITL/TPOT
throughput
total latency
```

MM+AR 可能改善 Decode ITL，却对 TTFT 很小；必须分开看。

---

## 10. DFlash 联合实验

矩阵：

```text
DFlash off/on
不同 speculative K
MM+AR off/on
q 1/2/4
small path off/on
```

同时采：

```text
acceptance rate
Target M histogram
每轮 accepted tokens
MM+AR path hit ratio
```

这样才能回答：

> MM+AR 的收益是自己变快，还是 DFlash 改变 M 后才出现/消失？

---

## 11. “边搬边规约”实验怎样先做上限分析

先从 profiler 量：

```text
T_batch_MM
T_batch_TX
T_tail_exposed
T_signal_fixed
T_wait_fixed
```

假设切成 c 个 chunk：

```text
潜在收益 <= 当前暴露 tail
新增成本 ≈ (c-1)*(signal/wait/control fixed cost)
```

如果新增成本已经接近上限收益，直接停止，不必编码。

这是性能研发中非常重要的“先算收益上限再写代码”。

---

## 12. 方案淘汰规则

一个新方案即使 microbench 更快，也应该回退，如果：

```text
端到端无显著收益
正确性范围变窄
Graph 不稳定
异常恢复明显变差
代码复杂度大幅上升但收益很小
只在非主流 M 区间获胜
```

性能不是唯一目标函数。

---

## 13. 建议实验报告模板

```text
### 假设
small-M 的主要瓶颈是 full-B weight stream。

### 证据
profiler / 对照实验显示……

### 方案
N-split，每核 256 列。

### 预测
M<=64 明显收益；大 M 不启用。

### Correctness
边界 M、q、Graph、1000 repeats。

### Micro
表格/时间线。

### E2E
Qwen + DFlash ITL/throughput。

### 结论
保留/回退；当前成立范围。

### 推翻条件
如果新 CANN 下 M-split weight floor 消失，则重测 threshold。
```

最后一项“推翻条件”建议以后成为每个优化报告的固定字段。

---

## 14. 最终目标：从手工调优走向自动决策

成熟演进：

```mermaid
flowchart LR
  A[人工 benchmark] --> B[自动 sweep]
  B --> C[shape performance DB]
  C --> D[offline autotune]
  D --> E[runtime policy]
  E --> F[workload-aware scheduler]
```

让 correctness 机制稳定，让性能策略由数据更新。

这比寻找“一组永远正确的 q/threshold/lookahead 常数”更现实。
