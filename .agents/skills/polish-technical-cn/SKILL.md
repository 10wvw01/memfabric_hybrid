# 中文技术文本润色（先可懂性，后风格）

黑话和 AI 味是两个独立问题。黑话是可懂性问题：读者认不认得这些词、拿没拿到该拿的信息；AI 味是风格问题：句式、标点、套话。处理顺序固定：

1. Pass 1 去黑话（内容 pass）：决定"说什么"——信息选择、分层、抽象级别；
2. Pass 2 去味（形式 pass）：决定"怎么说"——对 Pass 1 产物做句子级检查；
3. Pass 3 整卷校验。

顺序不能倒。Pass 1 会大面积重写句子，先做风格会在重构时丢弃已打磨的句子；黑话未清时，判断一句话是否 AI 腔并不可靠；黑话改白话的副产品是消灭大部分 AI 腔，反向不成立。

## 事实纪律

- 改写不改变证据状态。材料冲突或缺少关键依据时，回到相关实现或来源核查，不用行文补齐事实。
- 技术事实、术语原义、否定、版本、配置、数值、测量口径、来源与确定程度在两遍改写中保持一致。风格偏好不能把"未验证"改成"不支持"，或把"可能有额外开销"改成"性能更差"。
- 新增技术断言需要来源；没有源码或执行记录，按已有材料的来源和范围说明，不宣称亲自读过、运行过或验证过。
- 沿用用户指定的读者、篇幅、重点和交付方式。未指定时，读者按"熟悉相关编程基础、没读过这个模块的工程师"处理。

## Pass 1 去黑话

### 1.1 定读者与类型

读者决定术语基线（见 1.4），类型决定信息模板（见 1.3）。PR 与 commit 的类型取 prefix（fix/feat/refactor/perf/docs），无 prefix 从 diff 推断：行为变化带测试为 fix/feat，无行为变化为 refactor，带基准对比为 perf。文档与总结按用途归入最接近的类型。

### 1.2 四要素分层

任何交付都在向读者交代一个变化（delta）。首段四句话交代完：

- 基线：改之前是什么
- 动机：为什么现在改
- 改动：变成了什么
- 边界：什么不变、如何验证、代价

标题只保留"场景 + delta"。预算数字、验收方式、机制名、标识符不进标题，放正文。

### 1.3 类型模板

首段四问按类型展开，每类附带最容易犯的坑：

| 类型 | 首段四问 | 特有坑 |
|---|---|---|
| fix | 触发条件 / 根因 / 影响面 / 修法与回归 | 内部代号当"术语保真"，标题塞机制名与寄存器名 |
| feat | 现状差距 / 需求来源 / 新能力与默认值 / 边界与未覆盖 | "落地、全链、端到端"式断言无可验证含义 |
| refactor | 现状的结构代价 / 为何现在改 / 新结构 / 行为不变的验证手段 | 架构词（解耦、收敛、单一事实源）不落到具体所指；"为什么值得改"缺失 |
| perf | 基线数字与口径 / 瓶颈证据 / 改动 / 新数字与口径、代价 | 数字进标题前必须核实口径；口径不稳宁可不进 |
| docs | 空缺 / 补了什么 / 放在哪 / 给谁看 | — |

### 1.4 术语分级门禁

| 级别 | 例子 | 标题/首段 | 正文 |
|---|---|---|---|
| 团队通用词 | 平台名、产品名、通用工程词（kernel、超时、缓存） | 可用 | 可用 |
| 本模块内部词 | 机制代号、自造缩写、设计决策编号 | 换白话或删 | 首次出现带一句定义 |
| 实现标识符 | 寄存器名、宏与版本号、循环上限、文件名与行号 | 删 | 保留并说明作用 |

替换不是换成另一个词，是换成读者能直接理解的说法："epoch 自退"→"kernel 到点自己退出"；"全链可用"→给出可验证含义（哪个流程能跑通）或删。正文保留原标识符供定位。

### 1.5 结构清理（并入本遍）

三条规则原属风格，但作用于结构，前移到这里：删论述旁白（"值得注意的是""准确地说"）；同一边界只解释一次，结论表、正文、结尾不换句式重复防御；开头直接交代对象和问题，不写"本文将深入探讨"式预告。

完整源码长文、架构分析、实现对比与局部深入的展开方法，读 [explanation-patterns.md](references/explanation-patterns.md)。真实 PR 的逐词替换实例与背景段模板，读 [jargon-checks.md](references/jargon-checks.md)。

## Pass 2 去味

对 Pass 1 产物做句子级检查，此时应是轻量修改：

- 优先写清对象和动作；"进行分析"写成"分析"；不补造"我们发现""团队实测"。
- "契约"类直译词按实际含义拆开（参数要求 / 接口约定 / 行为保证 / 释放责任）；固定术语与代码标识按原义保留。
- 删不提供信息的修饰（全面、系统性、深度、赋能、奠定基础）；涉及真实范围与严格定义时保留。
- 直接写成立的命题及其范围，不用"不一定""不是说""不是……而是……"先虚后撤。
- 段落围绕实际问题，避免假反转、凑三点、四字排比、万能过渡和每段小结。
- 语气平实，不编造经历和情绪，不刻意口语化。
- 少用破折号；删装饰性加粗。

发现术语生硬、反驳句和套句反复出现，或需要改写方法与教学例时，读 [style-edits.md](references/style-edits.md)。

## Pass 3 整卷校验

按顺序过五关。任何一关不过，回到对应 pass 修完再继续：

1. 读者测试：只看标题和首段，默认读者能否回答本类型核心问题——fix：什么场景坏了什么、怎么修；feat：给谁加了什么能力、怎么用、默认行为；refactor：结构改成了什么、为什么值得、行为变没变；perf：快了多少、怎么测的、代价；docs：补了什么、给谁看。
2. 标题逐词过 1.4 分级表。
3. 首段四要素齐全，本类型特有坑逐条过。
4. 残余 AI 味扫描：破折号计数；"值得注意的是/换句话说/最后强调"类旁白；"不是……而是"防御句；装饰性加粗。
5. 事实保真：对照原材料逐项核对数值、版本、否定、口径、来源与确定程度；新增断言有来源；perf 数字未经核实不进标题。

## 背景知识

只有当某个概念能帮读者理解紧接的步骤、限制或差异时才补，解释完立即回到具体代码或流程。区分通用原理和本项目做法；冷僻、版本相关或有争议的事实需要核查，没有可靠依据的留为缺口，不为完整而编造。

## 代码、引用与图表

代码片段支撑紧邻的解释，保留改变行为的判断与必要上下文，改写后的代码标为示意。关键结论附近保留可定位的源码依据；运行结果注明来源与环境。表格用于同类项比较；代码标识用行内代码；不为版式堆叠标题、加粗或图表。

## 交付

默认交付最终文本，不附"已去黑话/去 AI 味"、自评分或工具过程；用户要求的修订说明另按需提供。只对发现的问题修改，改到关键内容完整且没有未处理的实质问题为止。
