# 去黑话的实例与替换方法

## 实例 1：fix 类标题的三轮演进（PR #8）

原始（AI 味与黑话并存）：

> fix(310p): epoch自退改壁钟计时修复28s monitor必杀缺陷——cntvct_el0预算15s+soak长驻验收

只去味的产物（错误示范——风格顺了，黑话全在，外人仍看不懂）：

> fix(310p): epoch 自退改壁钟计时，修复 28s monitor 击杀——cntvct_el0 预算 15s + soak 长驻验收

先去黑话的产物：

> fix(310p): 修复长驻场景协同 kernel 运行超 28 秒被系统强制结束——运行时长从按循环次数估算改为按时钟控制

逐词处置（对照 SKILL.md 1.4 分级表）：

- epoch：模块内部词，标题删；正文首次出现时定义为"kernel 的一次执行轮次"
- 壁钟：内部词（wall-clock 直译），换"读硬件时钟/按时钟控制"
- cntvct_el0：实现标识符（寄存器名），只进正文
- soak：行话，换"长稳验证"或删
- 28s：团队通用约束，保留，但补齐主体与后果——"被系统强制结束"
- 必杀/击杀：情绪渲染词，换"强制结束"

同一 PR 的首段四要素填充：

> 背景：AICPU 上单次任务连续运行不能超过 28 秒，超过会被系统直接杀掉整个 aicpu-sd 进程，且无法恢复（基线）。协同 kernel 原设计每约 22 秒自己退出、由 host 重新拉起，就是为了避开这条限制（原设计）；但 22 秒是按"循环次数 220000 × 假设每轮 100µs"估算的，实测每轮约 130µs，实际要 28.6 秒以上才退得出，长驻服务必被杀（失败原因）。本 PR 让 kernel 直接读硬件时钟、15 秒准时退出，并新增长时间运行验证（改动）。

## 实例 2：perf 数字进标题的翻车与修正（PR #5）

早期标题：

> feat(310p): AICore×AICPU协同模式迁移落地——SHM API在310P全链可用,流水加速8.02x

8.02x 进了标题但口径未核实。该数字后被本仓库示例 README 证伪：v2 kernel 尾部诊断固定睡 100ms，流水 1 次、串行 8 次的摊薄推高了比值；v3 修复后复测 2.57x。

作者后来的处置是标准答案：合并版标题删掉了数字，描述里专设"性能口径勘正"一节，写明被证伪的 8.02x/7.87x、复测 2.57x（占用态设备）、复现 1.91x（全新机器，两次稳定）及各自口径，并声明"历史数字仅作过程记录，勿作性能口径引用"。

perf 首段的正确填法（同一案例）：

> 基线与口径：串行 ×8 共 16.94ms（占用态设备）。瓶颈与改动：……。新数字与口径：流水 8×128KB 共 6.59ms，加速比 2.57x；该比值度量的是"批量流水合并提交相对逐轮往返"的收益，纯通算掩盖部分受 (T计算+T通信)/max(T计算,T通信) ≤ 2x 的结构上限约束。

规则：数字进标题前先核实口径；口径不稳（占用态设备、度量定义有争议）就不进标题，正文给全口径。

## 实例 3：feat 类描述的术语处置（PR #5 合并版原文）

合并版标题仍剩三个问题词：

> feat(310p): SHM设备发起SDMA协同模式迁移落地——AICore×AICPU邮箱化signal/wait/quiet设备侧自驱

- 落地：完成度断言，无可验证含义，删
- 邮箱化：机制比喻，换"kernel 内三原语收发"或删
- 设备侧自驱：内部词，换"搬运全部由设备侧完成"
- signal/wait/quiet：API 名（标识符），标题删，正文保留

改后：

> feat(310p): 迁移 AICore×AICPU 协同模式，SHM 设备发起 SDMA 在 310P 可用

描述术语处置对照（摘自合并版原文）：

| 原文 | 级别 | 处置 |
|---|---|---|
| 进程级单例（引用计数，多池共享） | 机制名 | "同一进程内多个池共用一份传输准备资源，最后一个池销毁时才释放" |
| wire 契约 | 内部词 | "host 与 kernel 共用的内存布局约定"（"契约"按含义拆开） |
| CP 流（DEVICE_USE_ONLY+rtStreamGetSqid） | 标识符 | 白话先说"设备侧专用流"，标识符降为括号注 |
| epoch 监督线程续命 | 内部词 | "监督线程在 kernel 到点退出后立即重新拉起"；epoch 首次出现给定义 |
| 存量缺陷修复① | 内部登记编号 | "顺带修复的既有缺陷"；编号是作者的工作记忆，不是读者的知识 |
| KFC 探测设备侧文件 | 工具名 | "经部署通道探测设备侧文件（mini_kfc）"，工具名进括号 |
| 双环全托管（零槽位算术/零清邮箱/零标志地址方案） | 机制名堆叠 | "双环邮箱由库管理：用户不用算槽位、不用清邮箱、不用记标志地址" |
| KVER bump 至 6（CP1 按文件名 dlopen 缓存） | 标识符 | "kernel 版本号升到 6（设备侧按文件名缓存，换名才能刷新）" |

从这批例子提炼三条规则：

1. 开发过程代号（E0a、P1、L2-④ 这类）是作者的工作记忆，不是读者的知识——正文也不留，只在"过程记录"类文档保留（本例早期版本有 E0a/F1-F20/三堵墙，评审后作者已自行删去）。
2. 比喻性内部词（邮箱化、血统、三堵墙、八坑）要么落成具体所指，要么指向已定义它的文档。
3. 实现标识符不删，但从"主角"降为"括号注"：白话先说做什么，括号里给定位符。

## 替换的常见模式

| 黑话形态 | 修法 | 例 |
|---|---|---|
| 机制代号 | 换成动宾白话 | "epoch 自退"→"kernel 到点自己退出" |
| 完成度断言 | 给可验证含义或删 | "全链可用"→"建池到设备侧收发全流程可跑通" |
| 架构词 | 落到具体所指 | "消除双头镜像漂移"→"两处重复定义改为共用一个头文件" |
| 行话 | 换通用说法 | "soak"→"长稳验证"；"smoke test"→"冒烟自测" |
| 情绪渲染词 | 换中性词 | "必杀/击杀"→"强制结束"；"根治"→"修复" |
| 无口径数字 | 核实后带口径，否则不进标题 | 8.02x 反例 |
| 机制比喻 | 落成具体所指或指向文档 | "邮箱化"→"kernel 内三原语收发" |
| 内部登记编号 | 删（过程记录类文档除外） | "存量缺陷修复①"→"顺带修复的既有缺陷" |

## 混合类型

一个 PR 兼有 fix 与 perf 时，按主 prefix 定模板，次要用一句话带过，两个模板不并排展开。类型判断看多数改动的意图；不确定时按最接近的类型处理，并在交付时注明所按类型。
