# 技术中文的改写方法

目标是让技术含义容易读懂。下面是按语境选择的编辑方法；不是禁词表，也不以出现某个词判断作者身份。

## 不要把证据边界写成连续反驳

技术文章需要限制结论范围，但限定范围不等于替读者反驳一个更夸张的说法。连续使用下面的结构，会让正文像答辩记录：

- “A 不一定说明 B”；
- “A 不是说 B，而是 C”；
- “A 并不意味着 B”；
- “这不是 X 的限制，而是 Y 的检查”；
- “换句话说，差异不在 X，而在 Y”。

先写当前材料实际证明的命题。证据停在哪里，也用事实交代：哪一步返回、哪个调用尚未发生、哪个配置没有覆盖。读者由此自然知道结论的范围，不需要每段再列一个更强的错误结论。

| 防御式写法 | 直接写法 |
|---|---|
| “这个错误说明后端没有接受该内存，不一定说明原生 API 不能处理它。” | “错误发生在后端的内存筛选阶段，此时尚未调用原生 API。” |
| “严格检查是实现所需能力检查，不是说这种内存是唯一合法类型。” | “该分支检查远端映射所需的句柄类型、地址范围和设备能力。”若文章没有讨论‘唯一类型’，到此结束。 |
| “这段代码不是说 A 不需要检查，而是两种类型的检查目标不同。” | “两个分支检查不同的前置条件：A 检查……；B 检查……。” |
| “启用 eager 不会自动解决类型检查问题。” | “eager 只改变注册时机；内存类型仍由类型识别和后端条件决定。” |

保留反驳句的情形很有限：用户的问题明确包含该前提；常见误解会直接导致错误操作；或者文章正在比较两个容易混淆的术语。即便如此，集中说明一次即可。后文写新增机制，不再用近义句重复排除同一误解。

编辑长文时，把结论表、正文、问答和结尾放在一起检查。以下组合通常造成重复：

1. 开头回答“能或不能”；
2. 正文解释机制后再次说“这不代表……”；
3. 问答区用“不一定”重述；
4. 结尾“最后强调一次”。

保留最适合承载证据的一处。开头需要摘要时，只写结论和条件；正文负责证明；结尾只有在需要给出选择或操作建议时才再次收束。

## 删除没有新增信息的论述旁白

模型常在事实前后加一层“阅读指导”：

- “这里最重要的是区分……”；
- “需要注意的是……”；
- “准确答案是……”；
- “换句话说……”；
- “这也解释了为什么……”；
- “最后再强调一次……”。

这些句式不是禁用词。判断标准是它们后面有没有新增技术信息。若下一句只改写上一段的结论，整句删除；若确有新的因果关系，直接写原因和结果；若需要概念对照，用对象作主语。

例如，前文已经说明模式只控制执行时点，后面无需再写“所以开启该模式并不意味着类型检查会通过”。直接进入类型检查的条件，或结束这一节。前文已经给出两条路径的步骤，也无需再加“换句话说，两者的本质区别在于……”，除非这句话引出了后文会使用的新判断标准。

每段至少应推进一项内容：新增事实、补充条件、连接调用关系、解释因果、给出证据或导出操作影响。只承担强调、归纳气氛或预防误读的句子，不算推进内容。

## 术语按原意使用

“契约”往往需要拆开。调用方的责任、实现提供的保证和一般规则不能互换：

| 当前意思 | 可选表达 |
|---|---|
| 调用前必须满足什么 | 参数要求、前置条件、调用条件 |
| 双方怎样配合使用接口 | 接口约定、调用规则 |
| 实现承诺返回或保持什么 | 行为保证、返回值说明、不变式（确指 invariant 时） |
| 数据按什么形式组织 | 数据格式、字段要求、格式规范 |
| 资源怎样持有和释放 | 资源使用要求、释放责任、缓冲区有效期 |
| 所谓“生命周期合同” | 生命周期要求、释放顺序、谁负责保持对象有效；按源码中的实际规则选择 |
| 哪些线程能在什么时候调用 | 线程使用限制、并发调用要求 |
| 文档规定的一组行为 | 该版本文档规定的要求、限制和保证 |
| Design by Contract 等固定概念 | 保留“契约式设计”等对应术语，按需解释 |

如果一个“契约”同时包含要求和保证，应分别说清；不能为了换词把它统一写成“约束”。原始代码、API 名称和准确引文不做风格替换。

相似判断也适用于其他词：

| 用词 | 普通说明中怎样具体化 | 应保留的技术语境示例 |
|---|---|---|
| 语义 | 返回值表示什么、操作会产生什么行为 | 语言语义、内存模型中的正式定义 |
| 对齐 | 确认一致、调整到同一配置 | 内存对齐 |
| 边界 | 有效范围、模块职责、具体限制 | 边界检查、明确的地址或权限边界 |
| 粒度 | 每次处理的单位或大小 | 锁粒度、调度粒度 |
| 闭环 | 写出实际发生的检查和处理步骤 | 闭环控制 |
| 底层逻辑 | 说明具体原理、条件或实现 | 确实需要区分的软件/硬件层次 |

术语和朴素说明可以并用。第一次解释对象时说清意思，后文使用同一个准确术语；不反复换近义词，以免让读者误以为出现了新概念。

## 常见句式的处理

| 表现 | 修改方式 |
|---|---|
| “在当前技术快速发展的背景下” | 从本文具体问题开始；保留真正决定行为的背景条件 |
| “本文将全面、系统、深入地分析” | 直接交代分析对象，或进入第一个实质判断 |
| “对异常处理路径进行分析” | “分析异常处理路径” |
| “通过构建……体系，实现……能力的提升” | 写清哪个组件做什么，实际产生什么变化 |
| “不仅……更……”或否定转折连续出现 | 有真实比较时保留；其余直接说结论，不制造额外对立 |
| “显著、高效、完善、先进”没有依据 | 写实际行为；无法证实程度时去掉程度判断 |
| “值得注意的是”“必须强调的是”反复出现 | 直接说明后面的条件或影响，让内容体现重要性 |
| 每节固定三点、每段末尾小结 | 按内容关系组织，合并重复解释，不凑数量 |
| “业界普遍认为”“我们实测发现”来源不明 | 核实来源，按真实主体表述，不用换主语制造依据 |
| “这为后续优化奠定坚实基础” | 给出具体、已知的后果；没有新增信息就结束 |
| 为显得自然加入“说白了”“你品”及夸张情绪 | 使用平实书面语，不编造经历、反应和语气 |

列表、标题、编号、括号和较长句子都可服务技术解释。不限制每句话的字数，不强制长短交替，不因为保留了“首先”或破折号就重写正确、易读的段落。

## 改写前后保留同一组事实

以下均为教学示例。数值、行为和来源只属于各例中明确给出的材料，不能搬到实际文章中。

### 条件与否定

原句：

> 在尚未完成内存注册的条件下，该后端在当前版本中无法对普通 host 页执行直接访问。

改写：

> 当前版本中，这个后端不能直接访问尚未注册的普通 host 页。

保留版本、后端、内存类型和未注册条件，不改成“设备不能访问 host 内存”，也不从必要条件推导“注册后即可访问”。

### 规则与具体动作

已知材料明确要求：异步提交后，调用方要保持缓冲区有效，直到完成通知到达。

生硬写法：

> 调用方必须遵循严格的异步生命周期契约，以保障底层访问语义的正确性。

改写：

> 提交异步任务后，调用方必须保持缓冲区有效，直到收到完成通知。底层在提交返回后仍可能使用这块缓冲区。

后一条解释来自给定材料，不进一步声称缓冲区一定被复制、固定或映射，也不把“保持有效”扩写成材料未规定的所有访问限制。

### 数据与确定程度

已知材料只有：当前实现缓存查询结果；可能减少重复查表；没有延迟测试。

生硬写法：

> 该缓存机制有效赋能了查询路径，并在一定程度上具备显著的性能优化潜力。

改写：

> 当前实现缓存查询结果，可能减少重复查表。现有材料没有延迟测试，实际效果还不能确定。

不能补造速度、倍率、测试主体或“已显著改善”的结论。事实已经足够具体时直接使用事实，不为了行文给未知信息加细节。

### 背景与当前实现

已知材料只有：某分支创建临时缓冲、执行两段复制后释放；作者动机没有记录。

生硬写法：

> 通过精心设计的中转机制，该架构构建了稳定高效的内存访问体系。

改写：

> 这个分支先申请临时缓冲，完成两段复制后再释放。临时缓冲连接了两次复制；现有记录没有说明作者为什么选择这条路径。

需要继续解释两次复制的执行主体或地址类型时，查相关实现后展开。不能把“中转通常用于处理可达性差异”写成这个项目已经证实的设计原因。

## 方法依据与适用范围

本文件采用 `stop-slop-cn` 中减少动词套壳、说明具体对象和消除重复结构的思路。技术写作还须保留证据要求，因此不采用自动删除不确定性、补造数字或经历、把所有术语替换成口语的规则。

此前调研提供了三个相关依据：英语写作实验观察到指令模型的名词化及文体偏好；奖励模型实验显示长度和格式可能干扰内容判断；翻译任务研究发现监督训练可能带入直译习惯。这些结果支持检查具体动作、信息价值和语境适配，不证明某个中文词必然错误，也不证明本 skill 已能改善所有模型的写作。[写作风格研究](https://arxiv.org/html/2410.16107v2)、[RM-Bench](https://arxiv.org/html/2410.16184v1)、[Lost in Literalism](https://aclanthology.org/2025.acl-long.630/)
