# SDMA inline reduce 三路对比基准报告

> **文档定位**：310P SDMA inline reduce 与搬运后 AICore 规约、纯搬运的三路性能对比数据与结论。
> **测试日期**：2026-11-03 | **环境**：Atlas 300I Duo（Ascend310P3）× 2 die, CANN 9.1.0, aarch64
> **读者**：评估 reduce 路径选型的开发与评审人员。

## 1. 测试问题

SDMA 引擎支持搬运时内联规约（`dst += src`，SQE opcode）。三条路径完成同一件事（把 r0 的数据加到 r1 的已有数据上）：

```
路径 A（基线）: r0 signal → SDMA 纯复制 → r1 wait（不算，只测搬运）
路径 B（两步）: r0 signal → SDMA 复制到 temp → r1 wait → AICore 标量循环 dst[i] += temp[i]
路径 C（一步）: r0 signal(ADD_FP32) → SDMA 搬运同时做 fp32 加（结果直接落 r1 的 dst）
```

需要回答：
1. **C 比 B 快多少**——inline 的性能收益
2. **C 比 A 慢多少**——inline 的额外开销

## 2. 方法

- 基准程序：`examples/memory_pool/01_basic/08_310p_aicore_aicpu_sdma/bench_inline_vs_copy.asc`
- 拉起方式：`mpirun -np 2`（r0 = 发起方，r1 = 接收方，同卡 die 对 dev4/dev5）
- **计时口径**：host 侧 wall time（kernel launch → stream sync），含 launch/sync 固定开销
  r1 侧耗时为主要指标（含等待收件 + 可选计算）
- **变量控制**（修正后）：
  - **预热轮**：每尺寸先跑 2 轮丢弃（消除冷启动/TLB walk/首次页表偏差）
  - **交错执行**：每轮按 A→B→C 轮流（消除执行顺序偏差；此前串行 A→B→C 导致 A 承担全部冷启动、C 最热，产生 -4%~-7% 假象）
  - **同一进程同一池**：三路共享同一 pool、同一 epoch kernel、同一邮箱，仅 mode 参数不同
- **正确性**：每尺寸每模式每轮 D2H 全量逐字校验 r1 的 dst 终值（含 4MB），全部 mismatch=0。
  校验逻辑：r1 的 dst 预填 100.0f，r0 发 N 轮 src=1.0f；
  A（纯搬运到 temp）期望 dst 不变=100.0f（证明搬运不动 dst）；
  B/C 期望 dst=100.0f+N（证明加法确实发生了 N 次——如果只是覆写 dst 会是 1.0f，
  如果没发生任何写则是 100.0f，mismatch=0 排除这两种可能）
- **矩阵**：5 尺寸 × 3 模式 × 3 有效轮（另加 2 预热轮）= **45 组有效数据 + 30 组预热**，全部通过

| 尺寸 | 每轮数据量 | 有效迭代数 | 预热迭代数 |
|------|-----------|-----------|-----------|
| 4KB | 1024 word (fp32) | 1000×3轮 | 1000×2轮 |
| 64KB | 16K word | 500×3 | 500×2 |
| 256KB | 64K word | 200×3 | 200×2 |
| 1MB | 256K word | 100×3 | 100×2 |
| 4MB | 1M word | 25×3 | 25×2 |

## 5. 分析

### 5.1 为什么 C（inline）零开销

SDMA inline reduce 比纯搬运多做一次**本地 HBM 读 + 本地 HBM 写**（读 r1 的 dst、写回 dst）。
这不构成瓶颈，因为：

- **跨 die 传输是时间主导**：1MB 跨 die 搬运约 91µs（≈11.5 GB/s），
  本地 HBM 读+写 1MB 仅约 2-3µs（≈400+ GB/s）
- **本地操作在传输期间流水完成**，不增加总时间
- fp32 加是 SDMA 硬件的旁路功能，不占额外流水线周期

```
A(纯搬运):  [跨die读1MB + 跨die写1MB]                            ≈ 92 µs
C(inline):  [跨die读1MB + 跨die写1MB + 本地读1MB + 本地写1MB]    ≈ 91 µs
             ↑ 本地操作与跨die传输重叠，不增加时间
```

### 5.2 为什么 B（搬运 + AICore 规约）极慢

B 的 AICore 侧是**标量循环**逐元素读改写（256K 次 load + add + store + 缓存行 clean）。
实测 AICore 吞吐恒定约 0.2 MB/s（各尺寸一致），远低于 SDMA 的 11+ GB/s：

- 1MB 时 AICore 循环独占约 4495µs（4587-92），占 B 总时间的 98%
- 循环吞吐 = 1MB / 4495µs ≈ 0.23 MB/s

```
1MB 时 B 的耗时分解:
  搬运:   ~92 µs（与 A/C 相同）
  AICore: ~4495 µs（标量循环 256K word 读改写加 + clean）
  总计:   ~4587 µs
```

### 5.3 尺寸趋势

- **4KB 时 C/B 仅 1.5x**：数据量小，AICore 循环只多 7µs，邮箱调度固定开销（~15µs）主导
- **1MB 时 C/B 达峰值 50.4x**：AICore 循环时间随数据量线性增长，比值在此取峰
- **4MB 时回落至 29.3x**：跨 die 带宽下降（~6 vs 11 GB/s），A 的绝对时间上升导致比值下降

### 5.4 测量偏差修正记录

初版报告曾出现"C 比 A 快 4~7%"的假象。根因与修正：

| 偏差来源 | 初版表现 | 修正方法 |
|---------|---------|---------|
| 执行顺序固定（A 最先、C 最后） | A 承担全部冷启动 | 交错执行 A→B→C 轮流 |
| 预热不足（3 轮含首轮冷启动） | A 首轮偏高 10~15% | 前 2 轮丢弃，只计有效轮 |
| temp 缓冲区首次 TLB walk | A 的信号目的页首次访问有额外开销 | 预热轮覆盖 |

修正后 C/A 开销收窄至 ±1.3%（纯噪声），结论不变：**inline 零开销**。

## 6. 结论

| 问题 | 答案 |
|------|------|
| C 比 B 快多少 | **1.5x ~ 50.4x**（1MB 峰值 50.4x；AICore 标量规约吞吐仅 0.2 MB/s） |
| C 比 A 慢多少 | **零开销**（±1.3%，噪声范围内；本地 HBM 读写与跨 die 传输重叠） |

**工程建议：在 SDMA 引擎支持 reduce opcode 的场景（SUM×FP32/FP16），
应使用 inline reduce（路径 C），可获得 1.5~50x 加速且无额外开销。**

## 7. 复现

```bash
cd examples/memory_pool/01_basic/08_310p_aicore_aicpu_sdma
# 编译(需 CANN + bisheng + MPI, 同 08 示例)
bisheng --npu-arch=dav-2002 -O2 -std=c++17 -w -x asc bench_inline_vs_copy.asc -x none \
    -o /tmp/bench_ic -DOMPI_SKIP_MPICXX \
    -I$OPENMPI_INC -I$CANN_INC -I../../../../../src/smem/include/host -I../../../../../src/smem/include/device \
    -Wl,--start-group $LIBS -Wl,--end-group \
    -L$MPI_LIB -lmpi -L$CANN_LIB -lascendcl -lruntime -ldl -pthread -lm
# 运行(空闲 die 对, ASCEND_RT_VISIBLE_DEVICES 选卡; 含 2 预热轮自动丢弃)
MF_SDMA_ORCH_JSON=<v32 json> ASCEND_RT_VISIBLE_DEVICES=4,5 mpirun -np 2 /tmp/bench_ic
```
