# 4-rank 协同模式测试报告

> **文档定位**：汇报 310P 协同模式（AICore×AICPU 设备发起 SDMA）从 2-rank 扩展到 4-rank
> 的方案、测试用例设计与真机实测结果。
> **读者**：评审本次合入的工程师，以及在 310P 上做协同 kernel 开发的同事。
> 机制细节（SQE 配方、提交链、缓存纪律）见[机制档案](./机制档案.md)，
> 行为契约见 `openspec/specs/smem/310p-sdma-orch/`。

## 1. 背景与结论

2-rank 协同模式（单卡双 die）此前已通过长稳验证（v28：双向 96000 封零丢失）。
它的邮箱协议按"每段只有一个对端"设计，在这个前提下是对的。4-rank（两张
Atlas 300I Duo，dev0/1 为卡0，dev2/3 为卡1）需求到来后，这个前提不再成立，
协议需要重构；同时跨卡的设备侧访问通路此前只经 host 拷贝验证过，设备侧
（AICPU、SDMA）路径属于首次验证。

本次交付：协议按对端划分重构（v30）、三处跨卡通路修复、主机仿真 UT 与
真机示例（`examples/memory_pool/01_basic/09_310p_aicore_aicpu_sdma_4rank/`）
两级测试用例。真机实测：**4 次连跑全绿**（全对全 12 有向对数据逐字校验零错、
交错序号连续性全过），08 示例（2-rank）在新协议下全量回归通过，2-rank 行为零变化。

## 2. 方案：从 2-rank 到 4-rank 改了什么

### 2.1 2-rank 协议的三条隐含前提

1. **到达环只有一个远端写者。** 2-rank 下对端 AICPU 写我的到达环，槽位按它
   自己的请求序号索引，安全。4-rank 下三个对端各持独立序号写同一环，
   槽位互相覆盖。
2. **请求序号在对端环上连续。** 2-rank 下我的请求序号全部发往唯一对端，
   在对端环上天然连续。4-rank 下序号跨目的地共享：给 Q1 发 0、给 Q2 发 1、
   再给 Q1 发 2，Q1 的环上是 {0,2}，接收方按"序号连续"消费的检查无法对齐。
3. **AICPU 可以直写对端内存。** 2-rank 是同卡跨 die，直写有硬件通路。
   跨卡直写没有通路（实测写入永远不完成，见 6.3）。

### 2.2 重构后的协议

核心变化一句话：**请求环与到达环都按对端划分，每对端一套独立的环和序号**。
旧布局保留区 48KB 单环，新布局 192KB：

```
段尾保留区(v30, 192KB):
  +0x0000  请求环 × 3, 每环 64 槽 × 32B      ← 本端 AICore 写(signal), 本端 AICPU 读
  +0x1800  reqTail × 3 / reqHead × 3          ← 生产/消费游标, 各自独占 64B 缓存行
  +0x1980  完成戳环 × 3, 每环 64 × u64        ← SQE 写, AICore quiet 逐环判定
  +0x1F80  邮件像暂存 × 3, 每区 512 × 32B     ← AICPU 写本端, 本端 SDMA 读
  +0xDF80  到达环 × 3, 每环 1024 槽           ← 对端 SQE 写, 本端 AICore wait
            (环内: 戳 1024×u64 + 邮件 1024×32B + 游标)
```

三条设计纪律：

1. **环下标是双射**。`环下标 = 压缩去自身(对端 rank)`：小于本端的对端原样，
   大于等于本端的减一。发送方写对端哪个环、接收方从哪个环收，用同一个公式
   （`SmemShmSdmaPeerRingIdx`，布局头单一事实源，AICore/AICPU/host 三端共用）。
2. **槽位、戳值、暂存内容都是环序号的纯函数**。这保住了一条既有性质：kernel
   异常退出后监督线程重新拉起，重新处理未确认的邮件时，会重写同样的槽位、同样的
   值，结果与首次执行完全一致（v28 长稳验证依赖的幂等性，4-rank 原样继承）。
3. **AICPU 不再直写对端内存**。到达邮件的内容（收件地址、长度、标签）先写在
   **本端**暂存区，连同数据一起由 SDMA 搬运指令投递。每封邮件四条指令：
   ①数据 ⓪邮件像（32B）②到达戳（8B）③完成戳（8B），同一队列按序执行，
   戳落地即邮件和数据都已到位。
设备侧 API 相应变为双形态：`wait(池地址, 对端)` 显式收指定对端的下一封，
`wait(池地址)` 轮询所有对端、返回值携带来源；`quiet` 逐环判定；`signal`
签名不变（目的地址自带路由）。参数结构与段尾布局用编译期断言锁死
（`HybmSdmaOrchParam` 80B，字段偏移固定），设备侧 kernel 版本号从 28 升到 30——设备按
文件名缓存 kernel，版本号即缓存键，防止新旧混载。

### 2.3 对称内存

所有段排在同一个固定基址（`0x12c200000000`）的窗口里，每 rank 一 GB 对称槽位，
本端 32MB 物理放在自己槽位，对端的 32MB 经 VMM 共享句柄导入后**也映射到它的
对称槽位**。于是任何一侧都能用纯算术定位任何对端：`对端段基 = dst & ~(对称段大小-1)`，
设备侧原语全程直接用池地址，不做地址翻译。2-rank 时代两 rank 共享同一设备
OS 的地址分配器，窗口起点天然一致；跨卡后两卡分配器独立，这条前提靠固定基址
预留（前序修复，issue #27）保证，本次实测四 rank 窗口基址全部相同。

## 3. 测试用例设计

两级用例分工：主机 UT 验证协议算术与布局不变式（进 CI，不依赖设备），真机
示例验证设备侧通路与数据正确性。

### 3.1 主机 UT：`test/ut/testcase/hybm/hybm_sdma_4rank_protocol_test.cpp`

在主机内存上仿真 4 个 rank 的段尾保留区，收发两侧复用与 kernel/设备原语同一份
布局常量与映射函数。9 个用例覆盖：环下标双射（全部 12 有向对）、布局不变式
（区块不重叠、64B 缓存行纪律、总量落 192KB）、路由往返一致（signal 侧
地址到环、kernel 侧环到目的 rank 互逆）、全对全投递、**多目的地交错无序号空洞**
（单发送方轮流发 3 个对端，各对端环内序号仍从 0 连续——2.1 表中第二条前提的
回归用例）、多发送方并发同一接收方、wait_any 归并收齐、单环溢出报错、契约
参数布局锁。

### 3.2 真机示例：09（结构）

| 项 | 设定 |
|---|---|
| 拓扑 | 2×Atlas 300I Duo，4 rank（devId = rank），每卡 P2P 槽位预算 4/8 通过（库内拓扑预检，超限建池即拒绝） |
| 池 | SHM + SDMA 位，每 rank 32MB，4 rank 对称窗口 |
| kernel | 每 rank 同一份 AICore kernel，MPI 4 进程拉起，host 零数据面 |

段内自定布局：出区 3×128KB（发往对端 p 的数据块，按对端索引）、入区 3×128KB
（来自对端 s 的数据块）、交错测试小块区、12MB 处一个判定词。

### 3.3 阶段①：全对全搬运

**设计意图**：验证多发送方并发写同一接收方时到达环的槽位隔离——这是 2.1 表中
第一条前提的直接检验。12 个有向对同时跑，任何一个环被写错都会在终态校验暴露。

**流程**（每 rank 对称执行）：

```
发: 每对端一块 128KB, 填 pattern(tag 含源/目的 rank, 可溯源) → clean → signal
    → quiet(等本端全部发出落地)
收: 统一收件循环, 收齐 3 封入件 + 3 封回件:
      入件(imm 未置回件位): 读改写 +INC → clean → signal 回件(imm 置回件位)
      回件(imm 置回件位): 只计数
    → quiet
判: host D2H 逐字校验本端出区: 每字 == pattern + INC
```

收件用**统一循环按 imm 类别位计数**而不是按调用次数，原因在真机调试中确认：
回件可能早于部分跨卡入件到达（跨卡比同卡慢），先到什么收什么的归并消费若按
次数结算，会把早到的回件当入件处理：对它再发一封多余的回件，收发双方此后
的收件计数全部对不上。按类别计数对任意到达顺序成立。

**判定**：4 rank 各自 mismatch=0/98304，判定词 PASS。

### 3.4 阶段②：多目的地交错序号连续性

**设计意图**：验证 2.1 表中第二条前提的修复——单环协议在交错多目的地下序号
必然断档，按对端划分后每环序号应连续无空洞。这是新协议最核心的性质，
单独设阶段而不并入①，是因为它要在 kernel 内逐封判定。

**流程**：每 rank 逐轮向 3 个对端交错各发一封 4KB 小块（imm=轮次），共 32 轮；
接收方对每个对端显式 `wait(池地址, 对端)` 逐封收齐，逐封校验三点：来源与
所等对端一致、环内序号等于首封基址加轮次（连续性）、imm 等于轮次（对账）。
序号用首封基址而非绝对值，是因为环序号跨阶段累计（阶段①已用掉每环 2 封），
校验连续性对前序流量不敏感。

**判定**：4 rank 判定词 PASS，任一封序号不连续、次序错误或标签不符，立即定位到对端与轮次。

### 3.5 可观测性设计

kernel 不能打印，异常路径全部落到**判定词**（段内 12MB 处的一个 32 位字）：
高 8 位魔数、4 位阶段、4 位对端、细分与错误码。异常即退（wait 超时/溢出、
路由非法、序号断档、拒投），host 读回解码，直接给出"哪个阶段、哪个对端、
什么问题"。

host 侧另有**状态观测线程**，每 5 秒读一次设备内存：常驻 kernel 的结果区
（返回码/消费数/退出原因——用于判断 kernel 在运行、已退出还是错误循环）、
判定词、三个到达环的游标快照（`对端=已消费数 E空/R就绪未收`）。出现就绪未收
的环时自动读出最近两封邮件内容（源/目的/类别位），用于定位投递到错误的环。
成功路径全程小于 5 秒，该线程无输出。

```bash
bash run.sh        # 一键: 环境自检 → (必要时)主构建 → bisheng 编译 → mpirun -np 4
```

整卡空闲、CANN ≥ 9.1、MPI 编译与启动同源。

## 5. 实测结果

环境：4×Atlas 300I Duo（8 die），CANN 9.1.0，空闲卡 dev2/3+dev4/5。

| 项 | 结果 |
|---|---|
| 阶段① 全对全 | 4 rank 各 mismatch=0/98304，耗时约 4ms |
| 阶段② 交错序号 | 4 rank 判定词 PASS（96 封/rank），耗时 <1ms |
| 稳定性 | 4 次连跑全绿，退出码 0，干净销毁 |
| 回归：08 示例（2-rank） | 新协议下全量 PASS（流水 mismatch=0、inline reduce PASS、加速比 2.07x） |
| 回归：UT | 协同相关 13/13，段管理相关 35/35 |

## 6. 真机首测暴露的三处跨卡通路问题及修复

跨卡设备侧通路此前只经 host 拷贝验证（host 拷贝走地址翻译层，不经过设备侧
直用池地址的路径），以下三处由本测试用例首次跑出并修复：

**6.1 跨卡导入未映射到对称槽位。** 跨卡导入原先映射到独立预留的地址，靠 host
拷贝层的地址翻译使用；设备侧原语直接用池地址访问该地址时触发页错误
（dmesg：`Reserve addr is invalid`，落在段尾最后一页）。修复：跨卡导入同样
映射到对称窗口槽位，固定基址保证两卡窗口起点一致。

**6.2 跨卡 P2P 使能缺失且设备号传错。** 跨卡导入路径此前跳过 P2P 使能（跳过的
依据是 host 拷贝探针，未覆盖设备侧）；且使能调用误传物理设备号，在设备重映射
（`ASCEND_RT_VISIBLE_DEVICES`）下报错或误使能同卡。修复：导入路径补双向
使能，并接入物理号到本进程逻辑号的换算接口。

**6.3 AICPU 跨卡直写无法完成。** 修复前两处后，kernel 仍停留在第一封跨卡
邮件的写入上（消费数停在首封，无报错、无退出）——设备侧 CPU 核的跨卡写入
没有通路（同卡跨 die 有，跨卡 PCIe 没有）。修复即 2.2 第三条纪律：邮件像经
本端暂存由 SDMA 指令投递，AICPU 对对端内存零直写。这与 hcomm 生产配方一致：
它的全部跨卡写也走 SDMA。

三处的定位过程依赖状态观测线程与判定词的数据（消费数、环游标、邮件内容读回），
这些观测能力保留在示例中，供后续排障复用。

## 7. 边界与遗留

- **8-rank 全互联不可达**：每卡 8 个 P2P 槽位是平台硬约束，全互联 8 rank 每卡
  需 12 槽，建池即被拓扑预检拒绝（`SM_NO_RESOURCES`，预期行为）。全互联上限
  6 rank，本次按 4 rank 交付。
- **长稳未做**：本报告的通过指 4 次连跑（秒级量级）。2-rank 时代的并发竞态
  类问题（507014）靠 96000 封/方向的长跑暴露，4-rank 需要同量级的 soak 后
  才能宣称同等置信度。
- **跨卡带宽未深入测量**：全对全耗时尚未拆分同卡/跨卡分量，已知跨卡带宽低于
  同卡（约 10-14 对 17-19 GB/s），供后续性能工作参考。
