# 双 Rank 并发丢件问题详解（错误码 507014）

## 一、背景：这套邮件系统是怎么工作的

### 1.1 出场角色

一张卡上有两个芯片（die A 和 die B），各自有内存，中间有连线。两个芯片**没有硬件缓存一致性**——谁写了什么，对方不会自动知道，全靠软件"写完主动刷出去、读前主动失效"来同步。

| 角色 | 位置 | 职责 |
|------|------|------|
| AICore（用户算子） | 各芯片 | 想要对方的数据时发请求；等数据到时盯着自己的签收簿看 |
| AICPU（搬运调度） | 各芯片 | 收到请求后，安排搬运引擎干活 |
| SDMA（搬运引擎） | 各芯片 | 只会一个动作："从地址 X 抄 N 字节到地址 Y"，不会写常数 |

### 1.2 两套邮箱

每个芯片的内存末尾有一块 48KB 的保留区，里面放着两套环形邮箱：

```
本端保留区（48KB）:
┌─────────────────────────────────────────┐
│  请求环（64 槽 × 32B）                    │ ← 本端 AICore 写，本端 AICPU 读
│  reqTail（AICore 写）                    │ ← "我发到第几件"   ──┐
│  reqHead（AICPU 写）                     │ ← "我处理到第几件"   │ 这三个字段
│  完成戳 64 个（SDMA 写）                 │ ← "第 N 件全干完了" ──┘ 在旧布局里挤在
│                                          │    同一条 64 字节缓存行里！
│  到达戳 1024 个（对端 SDMA 写）           │ ← 签收簿：接收方盯这里
│  到达邮件 1024 格（对端 AICPU 写）       │ ← 面单格：写着"数据落在哪、多长"
│  计数器（本端 AICore 写）                │ ← "我收到了第几件"
└─────────────────────────────────────────┘
```

**到达环是关键**：发送方（芯片 B）往接收方（芯片 A）的内存里写"面单"和"签收"，接收方 AICore 轮询自己的签收簿看到新单号就知道包裹到了。

### 1.3 正常流程

```
芯片B（发送方）                                芯片A（接收方）
                                              
① B 的 AICore 调 signal()
   写请求到 B 自己的请求环                     
   （本地写，不跨芯片，无风险）                 
                                              
② B 的 AICPU 读到请求，做三件事：
   a. 把"面单"写进 A 的面单格                  ═══跨芯片写═══→  A 内存：面单格
   b. 构造三条搬运指令给 SDMA
   c. 敲铃通知固件有新任务
                                              
③ B 的 SDMA 按顺序执行三条指令：
                                              
   指令①：把 4MB 数据从 B 搬到 A              ═══跨芯片写═══→  A 内存：数据落点
   （从来没出过问题）
                                              
   指令②：去 A 的面单格读 8 字节单号    ←═══跨芯片读═══   A 内存：面单格
           写进 A 的签收簿               ═══跨芯片写═══→  A 内存：签收簿
   （接收方就盯这个簿子）
                                              
   指令③：再去 A 的面单格读同一个单号  ←═══跨芯片读═══   A 内存：面单格
           写进 B 自己的回执簿              （本地写，不跨芯片）
   （用来确认"这单全干完了"）
                                              
                                               ④ A 的 AICore 轮询自己的签收簿
                                                  发现新单号 → 取件
                                                  更新计数器"已收到 N 件"
```

**一句话：指令①②③里的每次"跨芯片读面单格"，都是在读 B 刚写过去、可能还在路上的数据。**

---

## 二、问题现象

vllm-ascend 团队在长稳测试中偶发（约 21% 概率）双 Worker 同时挂死：

- 接收方永远等不到某一封邮件（签收簿里还是上上轮的旧单号）
- 但搬运调度那边"一切正常"：请求全处理了、任务队列排空了、错误码为零
- **没有报错、没有日志、没有痕迹——就是某封邮件"无声消失"了**

等了约 68 秒后，硬件看门狗判定芯片卡死，杀掉程序，报 507014。

## 三、三个根因

### 根因 1：两块芯片的写操作互相覆盖（确定性必现）

#### 问题在哪

旧布局中，面单数组的**最后一格（第 1023 号）**和接收方的**计数器**恰好挤在同一条 64 字节缓存行里：

```
保留区地址：
  ...  面单格[1021]  面单格[1022]  面单格[1023] |  计数器  |
  ...  0xA980        0xA9E0        0xAA00       |  0xAA20  |
                     ↑──────── 同一条 64 字节缓存行 ────────↑
                     [0xAA00 ~ 0xAA3F]
```

- 面单格[1023]：**对端 B 的 AICPU 写**（跨芯片远端写）
- 计数器：**本端 A 的 AICore 写**（本地写，**每收一封就写一次**，是接收方最热的变量）

两块芯片没有硬件缓存一致性，双方各自在自己的缓存里持有这条行。写完后各自做"整行回写"——**后到的把先到的覆盖掉**。

#### 出事时的慢镜头

```
芯片B的AICPU                          芯片A的AICore
    |                                     |
    | 写面单到A的第1023号格                |
    |   (跨芯片写，写还在路上)             |
    |                                     |  同时：刚收完上一封邮件
    |                                     |  写计数器 "已收到第 1023 件"
    |                                     |    (本地写，把自己缓存里的
    |                                     |     整条 64 字节行回写到内存，
    |                                     |     其中面单格[1023]位置
    |                                     |     还是旧值)
    |                                     |
    | 写到达了A的内存                       |
    | 但面单格[1023]的内存                  |
    | 被A的整行回写覆盖回旧值了！            | ← A 的回写晚到，把 B 的面单盖掉了
```

**结果**：面单格里是旧值。指令②去读面单读到旧单号，把旧值盖在旧值上——没有任何报错。

#### 代码位置

旧布局 `smem_shm_sdma_layout.h`：
```c
// 面单数组从 0x2A20 开始，1024 × 32B
constexpr uint64_t SMEM_SHM_SDMA_RS_ARR_MAIL = 0x2A20;
// → 最后一格 [1023] 在 0x2A20 + 1023×32 = 0xAA00

// 计数器紧跟在后面
constexpr uint64_t SMEM_SHM_SDMA_RS_ARR_HEAD = 0xAA20;
// → 0xAA00 和 0xAA20 在同一条 64B 缓存行 [0xAA00, 0xAA3F) 里！
```

写面单的代码 `hybm_sdma_orch_kernel.cc` `consumeOneMail()`：
```cpp
// 对端保留区基址（跨芯片地址）
const uint64_t peerRes = peerSeg + (p->physSize - SMEM_SHM_SDMA_RESERVED);

// 面单格地址（第 1023 号格 = peerRes + 0xAA00）
const uint64_t arrMailSlot = peerRes + SMEM_SHM_SDMA_RS_ARR_MAIL +
                             (seq % SMEM_SHM_SDMA_RS_ARR_SLOTS) * 32;

// AICPU 跨芯片写面单（4个字段 + 刷缓存）
am->seq = seq + 1;   // ← 单号写在这里
am->dst = mail.dst;   // ← 数据落点
am->len = mail.len;   // ← 长度
am->imm = mail.imm;  // ← 标签
cacheFlushLine(arrMailSlot);  // ← 刷出整条缓存行（64B），包含面单格+计数器位置
```

写计数器的代码 `smem_shm_aicore_base_sdma.h` `wait_at()`：
```cpp
// 接收方 AICore 本地写，也在同一条缓存行
SdmaWriteCell(res, SMEM_SHM_SDMA_RS_ARR_HEAD, head + 1);
// SdmaWriteCell 内部：写入 + DataCacheCleanAndInvalid(整条 64B 行)
// ← 整行回写，把 AICPU 刚写的面单内容覆盖回旧值！
```

#### 为什么只有第 1023 格出事

面单格每 32 字节一格，64 字节缓存行装两格。**其余 1023 格的"同缓存行邻居"是另一格面单——两个格子都由同一个 AICPU 写，不存在互踩。** 唯独第 1023 格的邻居是计数器——**对方芯片写的**。

#### 修复

布局重新排版，**不同芯片要写的字段各自独占一条缓存行**：

```
新布局（修复后）:
  ...  面单格[1022] | ← 独占末尾行  |  计数器（在 0xAA80，独占自己的行）
  ...  0xA9E0       |    0xAA00~0xAA1F    |  0xAA80
                     之间隔了至少 64 字节的空隙
```

```c
// 新布局
constexpr uint64_t SMEM_SHM_SDMA_RS_ARR_MAIL = 0x2A80;   // 面单从这开始
constexpr uint64_t SMEM_SHM_SDMA_RS_ARR_HEAD = 0xAA80;   // 计数器独占一条行
// 面单最后一格 [1023] 在 0x2A80 + 1023×32 = 0xAA7F
// 0xAA7F 结束后，计数器在 0xAA80——不同缓存行，永不互踩
```

### 根因 2：自己刚写过去的数据被自己人读到旧值（偶发）

#### 问题在哪

指令②和③要读的"单号"，**存在面单格里**（在对方芯片 A 的内存里）。这个值是 B 的 AICPU **刚跨芯片写过去**的。但"写过去了"≠"已经到了"——**跨芯片的写需要时间，还在路上时读回来的是旧值**。

```
芯片B                                      芯片A
    |                                          |
    | AICPU 写面单到 A 的某格                   |
    |   (跨芯片写，出发了但还在路上)              |
    |                                          |
    | SDMA 执行指令②：                          |
    |   "去 A 读面单格 8 字节"                   |
    |   读回来的是上一圈的旧单号                 | ← 面单还没到，内存里还是旧值
    |   把旧值写进 A 的签收簿                     |
    |   (旧值盖在旧值上，等于没写，无报错)         |
    |                                          |
    |   ......几微秒后......                    |
    |   (写终于到达了 A 的内存)                  | ← 新值到了
    |                                          |
    | SDMA 执行指令③：                          |
    |   "再去 A 读同一个面单格"                  |
    |   读回来的是新单号 ✓                       | ← 这时读到了新值
    |   写进 B 的回执簿                          |
```

**独有特征**：回执簿有新单号（③正常），签收簿还是旧值（②无效），旧值恰好差 1024（一整圈）。

#### 为什么串行模式不触发

串行请求-应答模式（如 08 示例）：
- 每次只有一封邮件在途
- AICPU 写面单后，SDMA 还要经过"敲铃→固件取指令→执行"的长链条
- 芯片间连线是**空闲的**，32 字节写在空载线上 1~2 微秒必到
- 等指令②真正去读时，面单早就到了

并发模式（V2 算子）：
- 双方向同时传输 4MB 大块数据，连线被挤满
- 32 字节小写被堵在大搬运的队尾，**到达时间从微秒变成几十微秒**
- 偶尔赶上指令②在面单到达之前就去读——读到旧值

#### 代码位置

问题出在指令②③的"抄写源"——用的是**面单格**（在对方内存里）：

`hybm_sdma_orch_kernel.cc` `issueMailSqes()`（修复前）：
```cpp
// 指令②：签收（源=面单格——在对方内存里！）
buildStarsSdmaSqe(sqe, streamId, seq + 1,
                  arrMailSlot,        // ← 源地址：对方芯片的面单格
                  peerArrStampSlot,   // ← 目的：对方的签收簿
                  8, ...);

// 指令③：回执（源还是面单格）
buildStarsSdmaSqe(sqe, streamId, seq + 2,
                  arrMailSlot,        // ← 源地址：还是对方芯片的面单格
                  quietSlot,           // ← 目的：自己的回执簿
                  8, ...);
```

**AICPU 明明有这个数（`seq+1` 就在自己寄存器里），却让 SDMA 跑到对方芯片去读"自己刚写过去但可能还没到"的值。**

#### 修复

让 AICPU 在**自己芯片**上存一份单号，指令②③从本端读（本地写本地读必定可见）：

```cpp
// 修复后：单号存到本端暂存区
const uint64_t stageSlot = reqBase - RS_REQ_RING + RS_STAGE +
                           (seq % RS_STAGE_SLOTS) * 8;
storeCell(stageSlot, seq + 1);   // ← 本地写，SDMA 本地读，必定可见

// 指令②改用本端暂存作为源
buildStarsSdmaSqe(sqe, streamId, seq + 1,
                  stageSlot,          // ← 源地址：本端暂存（不跨芯片）
                  peerArrStampSlot, 8, ...);

// 指令③同样
buildStarsSdmaSqe(sqe, streamId, seq + 2,
                  stageSlot,          // ← 源地址：本端暂存
                  quietSlot, 8, ...);
```

跨芯片动作只剩下**写**（跟从未失败过的指令①同一路径），不再有跨芯片"读自己刚写"。

### 根因 3：占位指令写法偶发卡住通道

#### 问题在哪

为了避免指令②③的队列尾值恰好等于 0（固件会把 0 当"空队列"忽略），在特定条件下会插入一条"占位指令"。旧写法用了**源地址=目的地址**的自拷贝：

```cpp
// 修复前：占位指令（src==dst，自拷贝）
buildStarsSdmaSqe(sqe, streamId, seq + 3,
                  scratch,   // ← 源地址
                  scratch,   // ← 目的地址 = 源地址！
                  8, ...);   //    从自己拷到自己
```

搬运引擎偶发卡在这种指令上，**后面跟着的真指令永远不被执行**。

```
芯片B                                芯片A
    |                                  |
    | 本封三连恰好使尾值=0              |
    | 先插入占位指令                    |
    |                                  |
    | SDMA执行占位指令:                 |
    |   "从 X 拷 8 字节到 X"           |
    |   固件卡住！                      |
    |                                  |
    | 后面的指令②永远不执行              |
    |   → 签收簿永远不更新               |  接收方永远等
    |   → 无报错、无声                  |
```

**双方向同窗丢件的原因**：两个 rank 步调一致（被同步栅栏锁住），同位置同时插占位指令，偶发同时卡住——两个方向各丢一封。

#### 修复

改成相邻字节互拷（源≠目的）：

```cpp
// 修复后：占位指令（src≠dst）
buildStarsSdmaSqe(sqe, streamId, seq + 3,
                  scratch,       // ← 源地址
                  scratch - 8,  // ← 目的地址 = 源地址减 8（相邻字节）
                  8, ...);
```

## 四、三个根因的共同点：为什么"查不出来"

| 根因 | 为什么无声 |
|------|-----------|
| 根因 1 | 面单被整行回写覆盖回旧值——指令②执行了，但把旧值盖在旧值上，前后无变化，无报错 |
| 根因 2 | 指令②执行了，但读到旧值把旧值写进签收簿——签收簿原本就是旧值，等于没写，无报错 |
| 根因 3 | 指令②根本没被执行——但队列看起来是空的（固件把卡住的指令当完了），无报错 |

**三个根因的表象完全一样**：签收簿是旧值、请求全消费、队列排空、错误码为零——**表面上和"什么都没发生过"无法区分**。

这就是为什么之前 vllm-ascend 团队定性为"邮件丢失"——表象上确实是丢了，但不知道丢在哪一步。
