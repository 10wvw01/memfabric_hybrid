> （三堵墙完整论证见历史提交 cdc44c67）。
>
> **读者**：需要把 AICPU 编排 kernel 部署到 310P3 设备 CP1 的开发者与运维人员。

## 1. 当前部署流程（2026-11-19 起：CP1 extend loader + 同名符号）

构建产物采用固定名称：`libmf_sdma_orch.so`、`libmf_sdma_orch.json`、
`libmf_sdma_orch_launch.json`。用户通过 `MF_SDMA_ORCH_DIR` 指定产物目录（库会在该目录下
递归查找三件套齐全的目录，必须恰好命中一套，0 套或多套都判失败），或者使用库的安装目录
发现逻辑（`<so 目录>/../hybm/aicpu_kernel/`）。json 内容只剩"定位 kernel 目录"的作用，
部署本身不再消费 json。

`smem_shm_create` 在 310P 选择 SDMA 后自动部署，**设备侧零手工操作**：

1. Host 读出 `libmf_sdma_orch.so` 字节，H2D 到设备内存；
2. 填 `DeviceArgs`（`aicpuSoBin`/`aicpuSoLen`/`deviceId`）并 H2D；
3. 经 `rtAicpuKernelLaunchExWithArgs`（libruntime.so，优先从已加载符号解析）
   以 KFC 方式启动 CANN 自带 `libaicpu_extend_kernels.so` 的
   `DynTileFwkKernelServerInit`；
4. 该 loader 在 CP1（`aicpu_scheduler`）进程内用 **memfd** 加载传入的 so
   （日志 `SaveSoFile: Create MemFile so success`），并按固定符号名填函数表；
5. 之后每轮以 `DynTileFwkKernelServer` 下发，`cfgdata` 指向 epoch 参数缓冲，
   CP1 内分发到本 so 的同名导出后转调 `HybmSdmaOrchEpoch`。

本仓 so 因此必须导出三个 loader 约定符号（`hybm_sdma_orch_kernel.cc` 文件尾）：
`StaticTileFwkBackendKernelServer`、`DynTileFwkBackendKernelServerInit`、
`DynTileFwkBackendKernelServer`。前两个是空实现，第三个从 args 偏移 40
（`DeviceKernelArgs.cfgdata`）取参数指针转调真实入口。

## 2. 为什么换链路

2026-11-18 驱动升级后 KFC 设备 shell（AICPU 内 `system()`）平台级失效：
`mini_kfc echo` 返回 507018，旧链路"迁移 + 复制到 CP1 搜索路径"整体不可用。
CUST（`cpuKernelMode=1`）句柄直发会把 kernel 送到 `aicpu_custom_scheduler`，
脱离 CP1（SQ 活查询 124 / mainRet 1424），方向被否。

extend loader 机制与 pypto 相同，实测在新驱动下完整可用：so 在 CP1 内加载执行，
不落设备搜索路径、不依赖设备 shell，因此也没有"异常退出残留文件"的清理问题。
设备侧加载物随 CP1 进程生命周期，无卸载接口（与 pypto 相同取舍）；Host 侧
H2D 副本在 Release 时释放。

## 3. 部署约束

| # | 规则 | 依据 |
|---|---|---|
| 1 | 目标机器 CANN 必须自带 `libaicpu_extend_kernels.so`（CP1 启动时预加载），且 CP1 上能取到 `DynTileFwkKernelServerInit/Server` 两个 api | 已验证 CANN 9.0.0 + 2026-11-18 驱动；日志见第 5 节 |
| 2 | 本仓 kernel so 必须导出三个同名符号，缺一个 loader 填表即失败 | loader 只 dlsym 固定符号名 |
| 3 | 每轮下发用 `args.timeout=0xFFFF` + flag `0x100`（`RT_KERNEL_USE_SPECIAL_TIMEOUT`）= 永不超时；每轮时长由 kernel 读主机报时计数自限（默认 15s） | runtime `ConvertAicpuTimeout` 语义；有限超时会把任务标记 507017 导致监督线程 sync 提前返回 |
| 4 | 进程内 `rtAicpuKernelLaunchExWithArgs` 优先从 `RTLD_DEFAULT` 解析，取不到才 `dlopen("libruntime.so")` | 新机器上不依赖 `LD_LIBRARY_PATH` 含 CANN lib64（ascendcl 通常已带入） |
| 5 | launch json 仍为 `KFCKernel`（type 5），设备侧系统监控不给该类型计时 | 平台事实 2026-10-08 定案 |
| 6 | NOTIFY 通道已证伪（不触发 + 流内 wait 挂死），通知链一律内存方案 | 机制档案第 1 节定论 5 |
| 7 | result/ovf buffer 必须 `ACL_MEM_MALLOC_HUGE_FIRST` | NORMAL_ONLY 落特殊段 SDMA 不可翻译 |
| 8 | 每进程单 SDMA 池（双环位于首个配置池段尾保留区） | ConfigureOrch 一次绑定约束 |

## 4. L0 OPP `.run` 的三堵墙与解锁条件（TODO-1）

产品终态（安装期部署）当前被推迟的根因，**全部实测**（xcclpp 包通道复现）：

| # | 墙 | 实测表现 |
|---|---|---|
| ① | 设备端 CMS 验签拒收无签名包 | `verifyFlag [Only Huawei]` |
| ② | 拒收**毒化宿主进程** | TsdOpen 失败 → `aclrtSetDevice` 507033——库形态不可接受的失败模式 |
| ③ | 解锁通道堵死 | `custom-op-secverify-enable` 开关容器内被拒需物理机；DCMI secverify 在 310P NOT_SUPPORT；user-certificate 需签发流程 |

**对照**：同为 OPP `.run` + AICPUKernel 的 `libcann_hybm_kernel.so` 在 A3 生产环境
工作——系 310P3 本机环境策略差异，非机制不可行。

**解锁条件（其一即可切 L0 并删自部署）**：拿到 user-certificate（官方第三方正解），
或目标环境验签开关可关闭。**通道侧无需改码**（包解压路径即 CP1 搜索路径）。

## 5. 部署回归（新机器验证清单）

1. 构建：`bash script/build_and_pack_run.sh`（或 `cmake -B build -DXPU_TYPE=NPU -DBUILD_PYTHON=OFF && cmake --build build -j`），
   确认 `build/src/hybm/ops/hybm_kernel/` 下有三个产物，且
   `nm -D libmf_sdma_orch.so | grep TileFwk` 能看到三个导出符号。
2. 运行 08 示例（任选一对空闲同卡 die）：
   `TEST_DEVICE_BASE=<n> bash examples/memory_pool/01_basic/08_310p_aicore_aicpu_sdma/run.sh`
   期望双 rank 打印 `=== EX08 r0/r1 PASS ===`，退出码 0。
3. 部署链路判据（设备侧日志，`/root/ascend/log/run/device-<die>/`）：
   - `Get api DynTileFwkKernelServerInit from so libaicpu_extend_kernels.so success`
   - 进程名必须是 `aicpu_scheduler`（CP1）；出现 `aicpu_custom_scheduler` 即走错链路
   - 需要 memfd 细节时开 `ASCEND_GLOBAL_LOG_LEVEL=0`，看 debug 日志里的
     `SaveSoFile: Create MemFile so success` 与三条 `kernelName ... has been loaded`
4. 失败定位：建池返回错误且日志有 `extend loader launch failed` / `sync failed` →
   检查目标机 CANN 是否带 extend lib、驱动版本是否满足；`json not accessible` →
   设 `MF_SDMA_ORCH_DIR` 指向构建产物目录（如 `build/src/hybm/ops/hybm_kernel`）。
5. 2026-11-19 回归结果：4 卡 8 die（0/1、2/3、4/5、6/7）全部双 rank PASS，
   8 个 die 的日志均确认 CP1 内加载。

## 术语注释表

| 术语 | 说明 |
|---|---|
| CP1 | 控制处理器核（`aicpu_scheduler`），AICPU kernel 的执行环境 |
| extend loader | CANN `libaicpu_extend_kernels.so` 里的 `DynTileFwkKernelServerInit`，在 CP1 内 memfd 加载传入 so 并填函数表 |
| 同名符号 | 本仓 so 导出的 `Static/DynTileFwkBackendKernelServer(Init)` 三个 loader 约定符号 |
| memfd | 匿名内存文件，loader 用它加载 so，不落设备搜索路径 |
| KFC | Kernel Function Call，`rtAicpuKernelLaunchExWithArgs` 的下发方式（type 5） |
| CUST | `cpuKernelMode=1` 迁移通道；其句柄直发落在 `aicpu_custom_scheduler`，不是 CP1 |
| OPP `.run` | CANN 算子包安装格式，安装期解压到 vendors 目录，产品终态部署形态 |
| CMS | 设备端包管理/验签组件，拒收无签名包的墙①来源 |
| user-certificate | 华为签发的第三方算子证书，墙③的正解解锁路径 |
