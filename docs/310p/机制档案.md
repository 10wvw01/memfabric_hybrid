## 1. 八个实测定论（先读，违反即踩坑）

| # | 项 | 定论 |
|---|---|---|
| 1 | AICore→AICPU 写可见性 | 天然一致（AICPU 裸读即见），无需 invalidate |
| 2 | AICPU→AICore 写可见性 | AICore DCache 双向陷阱（读侧 stale + 写侧滞留）；**dcci（`DataCacheCleanAndInvalid`，单缓存行失效）为正解** |
| 3 | AICore 大块 GM 写 | **必须 `ENTIRE_DATA_CACHE` clean**（SDMA 只认 GM/一致性点的数据） |
| 4 | 双 kernel 并发 | AICore 与 AICPU kernel 可同时常驻，无资源冲突（两条 stream） |
| 5 | 跨卡通知 | NOTIFY_RECORD **消费不等于执行**，310P3 上 notify/事件对**全弃用**——通知链一律内存方案 |
| 6 | 跨卡导出内存 | **必须 P2P policy 分配**（普通分配 import 报 507899） |
| 7 | AICore 计时 | dav-2002 无 cycle 计数器（`GetSystemCycle` 返回 0 且拖慢 8 倍，勿用）；等待段用 dcci 迭代数近似；AICPU 侧用 `cntvct_el0` |
| 8 | 轮询预算 | mode13 单 chunk 24000 迭代 ≈ 20s；mode14 按 chunk 数放大（共享预算不放大 → 前 chunk 偏慢耗尽后续预算误判超时）；总预算 < watchdog 30s |

> 真机实测定论（迁移必须遵守的纪律）。

补充两条 E0c 实测新结论（协同模式 SHM 语义的基石）：

- **AICore 可直接 GM 访问 AclVmm 池 GVA**（写 pattern / 读改写 INC / dcci 轮询池内
  标志全通）；
- **两侧 AICPU 同构 role0 成立**（"到达轮询 + ready 通知"上移 AICore 直接 dcci 池内
  标志，规避 AICPU 解引用池 VA，比 xcclpp 原版 role0/role1 非对称更简洁）。

## 2. SDMA SQE 64B 逐字节配方

SQE（Submission Queue Entry，提交队列描述符）是投给 TSFW 消费的搬运指令。
证据链：`AddOneMemcpySqeV2`（hcomm `aicpu_hccl_sqcqv2.cc:92-152`）、type 枚举
（`aicpu_hccl_sqcqv2.h:29`：`RT_HW_STARS_SQE_TYPE_SDMA=9`，`0x01` 是 AICPU
kernel-launch 类）、credit 常量（`ascend950/.../sqe.h:24` = 255）。

| 偏移 | 值 | 说明 | hcomm 源码出处 |
|------|-----|------|----------------|
| 0 | `0x09` | MEMCPY_ASYNC_SQE_V2 真实 type | aicpu_hccl_sqcqv2.h:29 |
| 4-5 | streamId | CP 流 rt_stream_id | `sqe->rt_stream_id` |
| 6-7 | taskId | | `sqe->task_id` |
| 8-11 | 全 0 | 0903 fresh dump 勘正 | — |
| 12-15 | credit=0xff | NEVER_TIMEOUT_KERNEL_CREDIT | sqe.h:24 |
| 16-19 | `00 de 0e 00` | opcode=NOT_ATOMIC + sro/dro/sns/dns/sssv/dssv 全 1 + overflow_en + qos | :116-132 |
| 20-21 / 24-25 | SMMU streamid | die0=0x7F45，die1=0xBF45 | :101-106 |
| 22-23 / 26-27 | ssid | 对称=实时查询值（`drvMemSmmuQuery`） | `src/dst_substreamid = ssid` |
| 28-31 | length | | `sqe->length` |
| 32-39 / 40-47 | src / dst（32+32 拆分） | | :123-127 |
| 48-51 | `00 00 20 00` | 模板原样 | overflow_en 位 :130 |
| 52-59 | overflow_addr | | :130-134 |

**纪律**：SQE 配方固件强相关，改动必须重新实机验证；streamid/ssid 按 die 区分
（实测 die0 ssid=2 / die1 ssid=5），不得写死假设。



## 3. 提交序列与流控

单笔提交序列（kernel 内）：

1. 读 shadow tail（先 `dc civac`）——shadow tail 是 host/kernel 侧维护的环尾影子指针；
2. 环满判断（`used = tail - head`）；
3. SQE 直写 slot（64B 逐字段构造，见第 2 节）；
4. `dc cvac` 逐 cacheline 刷（写侧 PoC）；
5. doorbell：GM 写 `sqRegBase+0x8`，或 `halSqCqConfig(SQ_TAIL)`（ioctl 路径，
   CP1 内 HAL devId = **die 号**）；
6. 回写 shadow tail。

**攒批模式**：只推进 shadow tail，整批一次 doorbell（hcomm 生产同款，
`dispatcher_aicpu.cc:926-932`）。

**SQE 对纪律**（协同模式跨端通知的基石）：数据 SQE + 标志 SQE（8B 哨兵搬运）
成对提交、一次 doorbell——SQ 环 FIFO 保序保证"标志到即数据到"。



## 4. CP 流与三流 launch 模式（host 侧）

host 在两条 stream 上并发 launch 双 kernel，加上取 sqId 用的 CP 流共三流：

| 流 | 创建方式 | 用途 |
|---|---|---|
| cpStream | `aclrtCreateStreamWithConfig(0, ACL_STREAM_DEVICE_USE_ONLY)` + `rtStreamGetSqid` | 只为取 sqId/streamId——SQ 注册进 CP1 进程 trs 表，是 kernel 内 `halSqCqQuery` 可查可投的前提 |
| launchStream | 普通流 | `aclrtLaunchKernelWithHostArgs(funcHandle, 1, launchStream, nullptr, &param, sizeof(param))` launch AICPU 编排 kernel |
| aiCoreStream | 普通流 | 用户 AICore kernel `<<<1, 0, aiCoreStream>>>` |

param（wire 契约）装配要点（demo :440-500）：`devId`=die 号（host 设备号 %2）、
`sqId/cpStreamId`、`submitMode`、`overflowAddr/resultAddr`（HUGE_FIRST 设备内存）、
`mailboxAddr/timelineAddr`、`role`（0=发送方 / 1=编排方）、`roleRsv[1]`=mode14
chunk 数、role0 的 `dstAddr`=对端数据区、`flagDoneAddr`=对端到达标志、role1 的
`dstAddr`=发起方结果区。



## 5. 通知链三件套与 cache 纪律

跨执行体（AICore/AICPU/对端）通信通道与 cache 动作对照：

| 通道 | 方向 | 配方 | cache 动作 |
|------|------|------|-----------|
| GM 邮箱 | AICore→AICPU | 16B/slot `{dataAddr, words}`，vector 直写 | 写后 `SINGLE_CACHE_LINE` clean；AICPU 读侧天然一致 |
| GM flag | AICPU→AICore | `*flag = value` | AICPU 写后 cvac + `dsb ish`；AICore 读前 dcci + volatile 读 |
| SQE 对 | 跨端数据+通知 | 数据 SQE + 8B 标志 SQE 一次 doorbell | FIFO 保序保证标志到即数据到；对端 AICPU `dc civac` 轮询标志 |
| 大块数据 | AICore 产出后 | — | AICore 写后**必须 `ENTIRE_DATA_CACHE` clean**（SDMA 只认 GM） |

**AICPU 不解引用池 GVA 纪律**：池地址只允许出现在 SQE 字段（src/dst），由 SDMA
经 SMMU 翻译访问——host CPU 解引用 VMM VA 会段错误，AICPU 同样不冒险；池内容
只经 SDMA 流动。

> 设计决策 D9、F14 推导。

## 6. 编排状态机要点（fork/改造 kernel 时对照）

- **role0（发送方）**：`cp1LiveQuery`（SQ 环 BASE/DEPTH/HEAD/TAIL 活查询）→ ssid
  查询（SMMU ssid 实时查询）→ 轮询邮箱（预算 24000×chunks）→ SQE 对
  （src=邮箱描述符地址，dst=param.dstAddr）→ 攒批 doorbell → head 前进诊断
  （2s 上限，TSFW 消费证据）；
- **role1（编排方）**：轮询本地到达标志 → 写 ready（透传 magic）→ 轮询回程邮箱 →
  回程 SQE 对 → doorbell；
- **mode14 流水**：mailbox ring 逐 slot、arrival/ready/result 标志数组逐 chunk、
  dst 逐 chunk 递增（`dstAddr + c*words*4`）、FIFO 保序只需等 `result[N-1]`；
- **timeline 打点**（`cntvct_el0`，16×u64 槽，0=关闭）：[0]入口 / [1]邮箱或到达
  命中 / [2]SQE 提交完 /（role1）[2]ready 写完 [3]回程邮箱 [4]提交完——性能基线
  与通信掩盖量化的数据源。

## 术语注释表

| 术语 | 说明 |
|---|---|
| SQE | Submission Queue Entry，提交队列描述符（64B），投给 TSFW 的搬运指令 |
| TSFW | 设备侧固件，SQE 的消费者，驱动 SDMA 引擎执行搬运 |
| SDMA | 设备间直接内存访问引擎，经 SMMU 翻译地址后跨 die 搬运 |
| SMMU | System MMU，设备内存管理单元，按 streamid+ssid 翻译池 GVA |
| ssid / streamid | SMMU 子流标识 / 流标识；die0 与 die1 取值不同，需实时查询 |
| CP1 / CP 流 | 控制处理器核及其提交流；`ACL_STREAM_DEVICE_USE_ONLY` 创建的流 |
| dcci / cvac / civac | 缓存行失效并清写 / 清写至一致性点 / 无效化（AArch64 cache 指令） |
| doorbell | 通知 TSFW "SQ 环有新 SQE" 的触发动作（GM 写或 ioctl） |
| shadow tail | host/kernel 侧维护的环尾影子指针，攒批时只推进它、最后统一 doorbell |
| GM 邮箱 | AICore→AICPU 通知的 16B 槽 `{dataAddr, words}`，位于协同工作区 |
| GVA | Global Virtual Address，MemFabric 全局统一编址的池地址 |
| AclVmm | CANN VMM（虚拟内存管理）接口族，310P 池化内存的创建路径 |
| watchdog | 设备侧看门狗（~30s，已实证：硬杀非终止 kernel/sync 507901/有界干净完成），kernel 轮询预算必须小于它 |
| mode13 / mode14 | 编排 kernel 双模式：单 chunk 八步闭环 / 多 chunk 流水 |
