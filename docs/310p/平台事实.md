> 全部条目经本机（4 卡 × 2 die，dev0↔dev1）实测。
>
> **读者**：在 310P3 上做适配、排查驱动/工具链差异、或评估平台能力的开发者。
> **注意**：这些是**本机实测定论**，驱动/CANN 版本变化可能改变结论，跨环境使用前

## 2. 行为差异与坑（F16-F20：适配中发现）

| # | 事实 | 证据 |
|---|------|------|
| F16 | 310P **不支持 SDID/SERVER_ID/SUPER_POD_ID 查询**（rtGetDeviceInfo 返回 207000）——已做容忍降级（310P 降级为无效值+WARN，可达性改由段映射状态判定） | e2e 实测（V2 改进：改用公开 API `aclrtGetDeviceInfo`） |
| F17 | join 重试会**重复 import 同一 shareableHandle** → 107017——Import 需幂等去重（按 rankId+sliceIndex） | e2e 实测（strace+日志定位） |
| F18 | 本地池地址分类依赖 reservedMap（AclVmm 段不登记）——`ClassifyAddressMask` 扩展：allocatedMap 命中且非 imported → LOCAL\|GLOBAL 双位 | e2e 实测（对 910B 行为等价） |
| F19 | **join 为动态成员语义**：先 join 的 rank 单成员即返回 OK，peer 映射在对端 join 完成后才就绪——使用方需在全员 join 后同步再拷贝（Barrier 模式即正确姿势） | e2e 实测（使用方契约） |
| F20 | `ReleaseSliceMemory` 存在 use-after-free（ASAN 独有检出，手工链接非 ASAN 版漏检）——已修复 | 正式 UT 二进制（ASAN+gcov）实测 |

## 3. 协同模式关键实测事实（机制细节见机制档案）

| 事实 | 出处 |
|---|---|
| SMMU 可译 AclVmm 池 GVA（含导入映射）——数据 SQE 的 src/dst 直接用池地址成立，Plan B（段层 IPC 导入）不启动 | E0b 轮A/轮B 双 PASS，数据全对 |
| **AICore 可直接 GM 访问池 GVA**（写 pattern / 读改写 INC / dcci 轮询池内标志全通）——SHM 设备发起语义的基石 | E0c 实测 |
| 两侧 AICPU 同构 role0 成立（通知上移 AICore 直接 dcci 池内标志） | E0c 实测 |
| die0 ssid=2 / die1 ssid=5（SMMU 子流按 die 区分，实时查询值） | E0c 实测 |
| **CP1 部署链（实测）**：每卡独立设备 OS 文件系统（dev2 看不到 dev0 部署的文件，`/usr/lib64/aicpu_kernels/0/` 路径各卡同名，die 对共享）；mode=0 加载**不校验**设备文件存在（dlopen 惰性到 launch，须显式探测）；CUST 迁移文件名**不含 host pid** 且 getfunc 返回值不可靠（正确入口名也 107000 但文件照样落盘）；KFC 设备 shell 工具箱极简——`stat/wc>重定向/md5sum/cksum/cmp` 缺失，`grep/awk/ls -l/顶层管道` 可用，`$()` 仅简单形式可用（文件校验用 `ls -l \| awk '{print $5}' \| grep -qx <size>`）；json 加载器要求 `.json` 扩展名（无扩展名 107000）；`cat $(可能为空)` 会退化为 stdin 等待挂死（须裸 glob 快速失败） | 本轮自动部署实机调测（KFC 布尔探针矩阵） |
| **【勘正 2026-09-18】"AICore 读 meta 恒为零"结论有误**——真因有二且均已在库内修复：① meta 区 AclVmm 映射缺 `AclrtMemSetAccess` 设备授权（池段有此步故 AICore 可读，`Hybm310PInitMetaGva` 遗漏）；② 设备头 `__gm__ void**` 解引用型 getter 在 dav-2002 后端读取错误。修复后 rank/rankSize/symmetricSize/工作区槽 kernel 内全部读对（EX_META 探针双 rank PASS） | P0a 实验实测（D2H 回读对照 + 四路判别探针） |
| **aicpu monitor taskTimeout=28s（勘正 2026-09-22，初记 ~30s）**：超时任务由 tsdaemon **杀整个 aicpu-sd 进程**（非任务级）——击杀者与宿主均为 `aicpu_scheduler`（aicpu-sd）：epoch kernel 经 launch json 加载进 **CP1（=aicpu-sd 进程的常驻调度环境，xcclpp 手册：`AICPUKernel` type=2→CP1，hcomm kernel 同宿主）**；`aicpu_custom_scheduler`（aicpu-custom-sd）是另一进程，**"CUST 迁移"仅为 KFC 文件落盘通道（`/home/CustAiCpuUser/lib`），落盘目录与执行进程无关**→ HDC 断连 → 进程内后续一切设备操作 507901（实测击杀于池创建 +29.07s）；launch attr TIMEOUT **不是**设备杀（host 同步语义）；有界运行干净完成；**恢复不可依赖**（wd_probe 曾见击杀后 KFC 通道仍活，serve 实测 HDC 断连不可恢复——结局取决于击杀时序，不可赌）；`usleep(100)` 实测 ≈130µs（粒度 1.3 倍）——**长驻任务必须壁钟自退（cntvct_el0 计时），禁止"循环次数×假设每轮耗时"算术**（22s 设计值按 100µs 算出，实际 ≥28.6s 必被杀）；epoch 壁钟预算 15s 留 13s 余量 | serve 场景设备日志（Init aicpu monitor successfully, taskTimeout=28s → HandleTaskTimeout → SendKillMsgToTsd: kill aicpu-sd）+ wd_probe 三连 + 前后两轮对照 |
| **monitor 超时不可由 host 配置；长驻正解 = 任务链续跑**（2026-09-22 逆向实证）：aicpu_scheduler 的超时值由 tsdaemon 下发（`libhost_aicpu_scheduler.so` 串证："Get opTimeoutEnable/value ... from ts success"、"Config OP execute timeout success"），host 侧无公开 API/env 旋钮（`AICPU_MODEL_TIMEOUT` 为 tsd 拉起 scheduler 时注入的进程环境，非用户通道）；hcomm 设备侧库 `libccl_kernel.so` 自带 `CheckTaskTimeout` + `WaitValue/CcoreWait`（硬件 wait SQE）等机制——**勘正（2026-09-22 源码精读）：hcomm 并非用翻转解决 28s，而是架构上不需要长任务**——AICPU 任务=编排提交 SQE+轮询等排空（`WaitFinishWhileLoop`，自有预算 960s 上限主动报错），等待远端数据用硬件 wait SQE（固件在流上等，不占 AICPU）、计算在 AICore、搬运是固件 SDMA——常态算子秒级完成根本触不到 28s；翻转实为算子级重试的流回放边界标记（profiler 门控），**>28s 的 hccl 算子同样会被杀**；`HCCL_EXEC_TIMEOUT` 是 hccl 自有任务预算，非 monitor 旋钮 | `strings` 逆向两库（符号/日志串/环境变量全集） |
| **翻转 SQE 与超时配置 API 的探究结论（2026-09-22，本轮实机五探针）**：① hcomm 翻转占位 SQE（`AddOneFlipPlaceHolderSqeV1`）实为**hccl 流重放边界标记**（绑定其 dispatcher/stream/taskId 记账，KFC 框架内仅 profiler 启用），TSFW 消费行为闭源——**非通用任务续跑原语，不可直接移植**；② runtime 源码存在公开 API 族 `aclrtSetOpExecuteTimeOut*/GetOpExecuteTimeout`（David 路径有 `TASK_TIMEOUT_SET` 下发链，`SetOpExecuteTimeOutV2` 返回成功且 `actual=credit×2.147s`），但**实机 3 次延长设置 + 32/40s 任务全部 507901**（固定 ~41s 返回 = host 侧晚 ~12s 才感知异步击杀），20s 对照干净完成。**plog 定案（2026-09-22 补证）**：三次击杀瞬间 `timeOut:1075200000 ticks ÷ tickFreq:38400000 = 精确 28.0s`（monitor 从未被延长），且全日设备日志中 `Get enable op execute timeout config from ts` **0 次出现**——已装 9.1.0 runtime 收下 API 调用（ret=0）但从不向设备调度器下发 `TASK_TIMEOUT_SET`（本机 runtime 源码的即时 David 下发链为更新版本行为，装的不带）。**结论：该 API 族在 CANN 9.1.0/310P 上为死路（升级 CANN 或提单确认前不可用）；长驻正解就是 epoch 壁钟自退+续命** | hcomm/runtime 源码逆向 + dev0 实机探针（20s 对照 PASS；32/40s×延长三连击杀）+ plog 三重证据（击杀 tick 值=28.0s / 配置行 0 次 / HandleTaskTimeout→SendKillMsgToTsd 与探针时间戳逐一对应） |
| **monitor"总闸"开关全景（2026-09-24 源码补录）**：`taskTimeoutFlag_` 为私有成员+私有 setter（零暴露，仅 monitor 初始化与 `SetOpExecuteTimeOut` 内部写）；设计内总闸实为 `closeMonitorFlag_`（`SetCloseMonitorFlag/IsMonitorClosed` 公开方法，`HandleTaskTimeout` 判定 `!taskTimeoutFlag_ \|\| IsMonitorClosed()` 任一断开即不杀）。三条官方触发链：① host `aclrtSetOpExecuteTimeOut*`（David，已证死路）；② tsd 事件 `Get opTimeoutEnable/value from ts`→`SetOpExecuteTimeOut`（`aicpusd_event_process.cpp:383`）；③ **2026 新版新增可 launch 伪内核 `CloseAicpuMonitor`**（`hwts_kernel_close_monitor.cpp`，`REGISTER_HWTS_KERNEL` 注册，参数 `monitorEn=1` 即关，配套 `NotifyCustCloseMonitor` 通知 cust 进程同关）。**9.1.0 实测三条全断**：本机 plog 全量 `opTimeoutEnable` **0 次**（tsd→sd 配置通道整体静默，非仅 enable 分支缺失）、击杀 tick 恒 28.0s、`CloseAicpuMonitor` 不存在——开关在设计里、一根线都没接进现网。新版补该伪内核说明官方在填此缺口，**升级 CANN 后超时开关族大概率转活**（提单/升级依据增强）。kernel 侧硬调 `SetCloseMonitorFlag`（同进程单例）不在 CP1 HAL 符号面（仅 `halSqCqConfig` 等弱符号），属拆全进程安全气囊，不做 | runtime 源码精读（`aicpusd_monitor.h:87-88/102/111/139`、`aicpusd_monitor.cpp:427-441/454`、`aicpusd_event_process.cpp:370-403`、`hwts_kernel_close_monitor.cpp` 2026 新增文件）+ 本机 plog 全量复核（opTimeoutEnable/CloseAicpuMonitor 均 0 次） |
| **CUST 迁移 json 基名配对**：加载器要求 json 文件基名与 .so 同名（异名 load 107000，json 内容与 .so 逐字节一致仍复现）；部署时 json 命名须为 `<soname>.json` | wd_probe 部署链二分实测（同名即通/异名即败） |
| **bisheng dav-2002 工具链约束（910B 后端无此限制）**：运行时整数→`__gm__` 指针 cast 会错位——`(__gm__ void*)` 型恒 +0x2000（-O0/-O2 均错）、变量绑定型 u64 cast 在 -O2 错位（-O0 正常）、经该指针写读错位；而编译期常量地址的标量立即解引用、kernel 参数传递的指针、指针算术均正常。**设计纪律：kernel 内勿物化整数 cast 出的指针（变量绑定/下标恒偏）；`*(volatile __gm__ T*)(运行时整数)` 的立即解引用（T1 实测）与 kernel 参数指针算术可用——V5 设备头全部建立在两者之上**（910B rdma 代码的 `SetGlobalBuffer((__gm__ uint32_t*)runtimeAddr)` 同款模式在 310P 不可用） | EX_META 探针 A/B/C 三路判别（-O0/-O2 对照）实测 |
| 流水加速比实测（8×128KB）：8.02x→7.87x（文件会合口径，实为 100ms 尾睡摊薄假象）→ **2.0~2.3x（V3 kernel 修复尾睡后诚实口径）** | 08 示例历轮实测，V3 kernel 修复尾睡后重测 |
| 310P 的 AICore（dav-2002）**不能投 STARS SQE**（无该路径）——协同模式用 AICPU 代投 | 迁移动机，历史实测 |

## 4. 工具链差异笔记（bisheng / hcc / dav-2002）

| # | 坑 | 正解 |
|---|---|---|
| T1 | AICore kernel 编译：AIV_ONLY 被拒 | `--npu-arch=dav-2002` + `KERNEL_TYPE_AICORE` |
| T2 | bisheng 的 `-x asc` 会把后续 `.a` 也当源码 | 显式 `-x none` 切回 |
| T3 | clang/lld 链接缺数学库 | 显式 `-lm` |
| T4 | AICore kernel 内**不支持 lambda** | 辅助函数用文件级 `__aicore__ __inline__` |
| T5 | `__gm__` 限定只出现在 kernel 形参 | host 调用侧用普通指针；`static_cast<__gm__ T*>` 报 "casts away qualifiers" |
| T6 | AICore 侧无可用 cycle 计数器 | 等待段用 dcci 迭代数近似；AICPU 侧 `cntvct_el0`（机制档案定论 7） |
| T7 | bash 陷阱：`export X && cmd0 & cmd1 &` 中 `&` 优先级使 export 只作用于第一个后台子 shell | 双进程脚本显式在子命令内 export 或用 `env` 前缀 |
| T8 | 新增源文件后 CMake GLOB 不自动收编 | 重新 `cmake -B build` configure 再 build，否则链接旧档案报 undefined reference |
