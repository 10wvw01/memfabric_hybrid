# 平台适配开发工作法

> **文档定位**：流程规范（全仓库适用，不限 310P）。提炼自两次 310P 大实践——
> 2-rank VMM 内存池化（《310p-2rank-vmm-开发计划.md》）与 AICore×AICPU 协同迁移
> （技术沉淀见 `docs/310p/` 档案）——两次工作独立走出了同一条路径，本稿将其
> 显式化。源实践均已实机验收（V1: 3/3 轮全绿；V2: 八步闭环 mismatch=0、流水 8.02x）。
>
> **读者**：下一次平台适配/大型机制迁移工作的负责人。

## 1. 九阶段流程总览

```
上游方案 ──→ 实机探测 ──→ 开发计划 ──→ P0 可行性关卡 ──→ WP 产品化
(方案文档)   (F-表/X结论)  (D-表/E/M)   (E实验+判据表)     (代码+挂载点表)
                                                          │
 文档同步 ←── PR 清理 ←── UT+基线对照 ←── 示例验收 ←────────┘
(档案/spec)  (checklist)  (用例+对照表)   (example+README)
```

| 阶段 | 做什么 | 产物 | 关键纪律 |
|---|---|---|---|
| 1. 上游方案 | 吃透方案文档的决策与验证项 | 方案文档（含 D 决策编号、V 验证项编号） | 先有编号体系，后续全程引用 |
| 2. 实机探测 | probe 工具实测硬件/驱动/符号能力 | F-表（事实+证据+影响） | **每个事实必须有实测证据**；probe 不进仓库 |
| 3. 开发计划 | 计划文档定稿 | D-表（决策）、E-关卡、M-里程碑、风险表 | 挂载点先论证再动手；引用 F 编号不重复展开 |
| 4. P0 可行性关卡 | 用最小实验裁决最大技术未知点 | E 实验 + 判据表 + 明确出口条件 | **每个 E 实验预设通过/失败两个出口**（如 Plan B）；探针属开发过程，不进产品分支 |
| 5. WP 产品化 | 按工作包落地代码 | 代码 + 挂载点表（每处既有代码改动可核对） | 途中发现的**存量缺陷单独编号登记**（如修复①②），不与新增混述 |
| 6. 示例验收 | 端到端实机示例 | example + README（判据 + 实测数字） | README 必含验收标准与运行命令，数字可复现 |
| 7. UT + 基线对照 | 单测覆盖新路径 + 存量回归 | UT 用例 + 基线对照表 | 环境性失败必须**纯基线对照**证实（同版本代码复现相同失败），不得归因于新改动 |
| 8. 文档同步 | 知识归位 | `docs/<平台>/` 档案/openspec spec/API 文档 | 按第 4 节生命周期约定各归其位 |
| 9. PR 清理 | 删除探索过程产物 | 干净的产品 PR | 按第 3 节 checklist 四步执行 |

## 2. 三种核心表格样例

### 2.1 F-表（实机探测事实）

```markdown
| # | 事实 | 证据 | 对计划的影响 |
|---|------|------|-------------|
| F12 | export 必须带 DISABLE_PID_VALIDATION，否则对端 import 被拒 507899 | probe + strace 实证 | Export 固定 flags=0x1 |
```

要点：事实一栏是**可判真假的陈述句**；证据一栏是**可复现的命令/路径**；影响一栏
回链计划决策编号。

### 2.2 D-表（设计决策）

```markdown
| # | 决策 | 内容 | 理由（含被否备选） |
|---|------|------|------|
| D4 | 挂载点 = InitTransManager | 310P 分支挂在 SDMA 传输准备处 | SHM 跳过 InitDataOperator；URMA 在 OpenDevice 加载 kernel 是同族先例 |
```

要点：每条决策必须**记录被否掉的备选**——没有备选对比的决策无法复核。

### 2.3 判据表（验收关卡）

```markdown
| 判据 | 期望 | 实测 |
|---|---|---|
| headAfter | 0→2（TSFW 消费 SQE 铁证） | 0→2 ✓ |
| 数据校验 | mismatch=0 | 1024/1024 ✓ |
```

要点：判据在**实验设计时预先写死**（防止"跑出来什么就认什么"）；一列期望、
一列实测，全部可机判。

## 3. PR 清理 checklist（删探索过程产物时必跑）

> 教训来源：ec1ee588 清理提交删 14 个文件后留下四处引用残留（表格断裂、重复行、
> 失效指向），根因是删文件与改引用两步之间没有核对机制。

```markdown
- [ ] 步骤1 删文件：git rm 探索产物（probe/deploy 工具/一键脚本）
- [ ] 步骤2 grep 全部引用：对每个被删路径 grep 仓库（源码注释、文档、README、
      能力矩阵索引），形成引用清单
- [ ] 步骤3 逐条修订：清单内每处引用改为指向保留的文档（验收判据与实测数字
      必须在保留文档中有落点），修订时注意表格行不被 blockquote 切断
- [ ] 步骤4 完整性复查：被改文档重新通读相关小节——表格连续（无孤立行）、
      交叉引用（"见 X.Y 节"）目标存在、同节内无重复条目
```

## 4. 文档生命周期约定（四类去处）

| 类型 | 生命周期 | 去处 | 更新规则 |
|---|---|---|---|
| 技术档案（配方/部署/平台事实） | 10 年 | `docs/<平台>/` | 直接编辑演进；与过程记录冲突时以档案为准 |
| 行为契约（SHALL/MUST 级） | 架构存续期 | `openspec/specs/<capability>/` | 只能经 OpenSpec change 的 delta 变更，归档合入 |
| 过程记录（计划/进展/验收历史） | 冻结 | 仓库根目录，头部加冻结指针 | 完成即冻结，不再更新 |
| TODO（backlog） | 待办 | 过程记录的 TODO 章节 | 被捡起时立新计划文档/新 change，原条目标注去向 |

## 5. 构建与测试纪律（速查）

- **构建双模式互斥**：UT 构建与实机 e2e 构建不能共用同一份 build 目录（详见
  《310p-2rank-vmm-开发计划.md》附录 A1）；
- **禁止绕开仓库脚本自建构建目录**（附录 A2，产物路径有约定语义）；
- **mockcpp 机器码打桩与 ASAN fake-stack 存量不兼容**：全量 UT 用逐套件独立进程
  模式取得确定性结果（附录 A4）；
- **新增源文件后 CMake GLOB 不自动收编**：必须重新 configure 再 build（工具链坑
  速查见 `docs/310p/平台事实.md` 第 4 节 T 表）。

## 术语注释表

| 术语 | 说明 |
|---|---|
| F/D/E/M 编号 | 实机事实 / 设计决策 / 可行性实验 / 里程碑的全程唯一引用编号 |
| probe（探针） | 阶段性实验工具，验证机制可行性用，不随产品 PR 合入 |
| 挂载点表 | 产品化阶段"改了既有代码哪些位置、为什么"的逐处核对清单 |
| 纯基线对照 | 用未含新改动的代码复现相同失败，以证明失败与改动无关 |
| Plan B | P0 实验失败出口的备选方案，实验设计时预置 |
