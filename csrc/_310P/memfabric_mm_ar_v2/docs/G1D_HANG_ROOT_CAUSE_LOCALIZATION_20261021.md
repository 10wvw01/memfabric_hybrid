## 一、一句话结论

**挂死源头在 MemFabric 的发送落地链（AICPU 编排器 → SQE → CP/SDMA 硬件执行 →
对端保留区写入），不在 V2 融合算子的实现逻辑里。** V2 的核心被证据链逐项洗清：
它正确地发出了请求、正确地在等待、等待的东西确实没有到达——而"东西没到达"
发生在 MemFabric 负责的最后一段路上。

---

## 二、通俗模型：这是一个"快递柜"故事

把跨卡通信想象成两个小区之间的快递系统：

```
     rank0 小区 (dev0)                          rank1 小区 (dev1)
  ┌────────────────────┐                    ┌────────────────────┐
  │ V2算子 = 收件人      │                    │ V2算子 = 收件人      │
  │ 反复查看 440 号柜    │                    │ 反复查看 442 号柜    │
  └─────────▲──────────┘                    └─────────▲──────────┘
            │ 查                                       │ 查
  ┌─────────┴──────────┐                    ┌─────────┴──────────┐
  │ ARR到达环 = 快递柜   │                    │ ARR到达环 = 快递柜   │
  │ 柜440: 旧单据(7609)  │                    │ 柜442: 旧单据(7611)  │
  │ 期待新单据 8633 ✗    │                    │ 期待新单据 8635 ✗    │
  └─────────▲──────────┘                    └─────────▲──────────┘
            │ 派送                                      │ 派送
  ┌─────────┴──────────┐                    ┌─────────┴──────────┐
  │ rank1 的 AICPU 快递站 │ ──── SDMA 硬件 ───▶ │ rank0 的 AICPU 快递站 │
  │ 接单(reqSeq 8636)    │      派送途中丢失!     │ 接单(reqSeq 8634)    │
  │ 队列清空、打烊下班    │      ✗✗✗             │ 队列清空、打烊下班    │
  └────────────────────┘                    └────────────────────┘
```

D1R4 那天发生的事（observed）：

1. rank1 的收件人（V2 算子）把 chunk0 的搬运单**交给了自家快递站**，快递站
   **接了单、出了库、队列清空下班了**（控制面全绿）；
2. 但 rank0 小区 440 号柜里**始终没有出现新单据**——柜子里还是上一轮
   （1024 单之前）的旧单据；
3. rank0 的收件人就站在 440 号柜前**永远等下去**；
4. rank0 等不到 → 它自己也有一单（chunk2）没发出去 → rank1 的收件人在
   442 号柜前也永远等下去（**级联受害者**，不是独立故障）；
5. 8.7 秒后硬件看门狗把两边的算子核心都判了超时（507014）。

## 三、证据链（六步，每步文字说明 + 代码佐证）

### 证据 ①：卡死的位置——V2 核内的等待原语，不是计算、不是校验

**日志实值（D1R4 停滞帧，observed）**：

```
[V2_G1C] rank=0 c0=1730:0:50 c1=1730:0:60 ...   ← 0号核停在阶段50，其余7核停在60
[V2_G1C] rank=1 c0=1730:2:50 c1=1730:2:60 ...
```

**代码佐证** `csrc/_310P/memfabric_mm_ar_v2/src/op_kernel/mf310p_v2_kernel.asc:85-97`
（G1-D 埋点后的两处等待之一）：

```cpp
if (core == 0) {
    G1cStage(status, core, prev, 50);              // ← 停在这里：进入等待
    auto mail = smem_shm_sdma_wait_at(reserved);   // 等待对端到达邮件
    G1cStage(status, core, prev, 52);              // ← 没到这：wait 从未返回
    G1dWaitResult(status, core, prev, mail);
    const bool good = mail.status == ... ;         // ← 更没到这：校验从未执行
    if (!good) G1cStage(status, core, prev, 53);   // ← 没到这：不是校验失败
    CheckOrTrap(good, status, 2);
    G1cStage(status, core, prev, 51);              // ← 也没到这
}
```

**人话**：阶段编号 50→52→(53/51) 是 G1-D 专门埋的"探照灯"。两边的 0 号核都停在
**50（wait 之前）**，从未走到 52（wait 返回）或 53（校验失败）。
→ **wait 永远没有返回，且 V2 自己的邮件校验代码根本没机会执行**——
V2 的校验逻辑首先被洗清。

### 证据 ②：它到底在等什么——游标数学（理解全案的钥匙）

**代码佐证** `memfabric_hybrid/src/smem/include/device/smem_shm_aicore_base_sdma.h:156-176`
（MemFabric 等待原语）：

```cpp
smem_shm_sdma_mail_t smem_shm_sdma_wait_at(__gm__ uint8_t *res)
{
    const uint64_t head = SdmaReadCell(res, SMEM_SHM_SDMA_RS_ARR_HEAD); // ① 读"我已消费到第几件"
    const uint64_t expect = head + 1;                                   // ② 下一件的单号应为 head+1
    for (uint64_t i = 0; i < 100000000; i++) {                          // ③ 最多轮询1亿次
        stamp = SdmaReadCell(res, ARR_STAMP + (head % 1024) * 8);       // ④ 只盯一个柜子：第 head%1024 号
        if (stamp == expect) break;                                     // ⑤ 单据出现 → 取件
        ...
    }
    ...
    SdmaWriteCell(res, SMEM_SHM_SDMA_RS_ARR_HEAD, head + 1);            // ⑥ 取件后自己推进游标
}
```

**人话**：`ArrHead` 是**收件人自己的消费进度**（取一件 +1），不是快递站的发货量。
收件人只盯着**一个柜子**（`head % 1024` 号）反复看，看到单号等于
"我已取件数 + 1"才算到货。

**代入 D1R4 实测数（derived）**：

| | rank0 / dev0 环 | rank1 / dev1 环 |
|---|---|---|
| 消费游标 ArrHead（冻结值） | 8632 | 8634 |
| 它盯的柜子 | `8632 % 1024` = **440 号** | `8634 % 1024` = **442 号** |
| 它期待的单号 | **8633** | **8635** |

### 证据 ③：柜子里是什么——**旧单据，说明新单据从未被放入（本案最关键一锤）**

**日志实值（D1R4 停滞期 Host 采样，`[MF_G1D]` 行，observed）**：

```
dev0: arrHead: 8632 headSlot: 440 headStamp: 7609  ← 盯的正是440号柜，里面是7609号旧单
dev1: arrHead: 8634 headSlot: 442 headStamp: 7611  ← 442号柜里是7611号旧单
```

单号绕柜规律：440 号柜循环存放单号 441, 1465, …, **7609**（上一圈），**8633**
（下一件应放这里）。`7609 = 8633 − 1024`，**整整差一圈**。

**人话**：G1-D 采样器读的"动态头槽"（`ArrHead % 1024`）**恰好就是收件人盯的
那个柜子**（两者用同一公式算槽位）。Host 用 DMA 直接读显存，读到的是 **7609**；
AICore 用 volatile load 轮询，永远等不到 8633。**两条完全独立的读取路径看到
同一个旧值**——不存在"写进去了但读不到"（缓存可见性）的可能：如果真写进
显存了，Host 的 DMA 读一定能读到。

**同时段同一次快照的旁证**：0/1/2 号柜读到了**本圈新单**（8193-8195），
证明 Host 读取路径完全正常，唯独 440 号柜没有新单。

→ **判定：单据从未被放进柜子（写入丢失），而不是"放了但看不见"。**

### 证据 ④：寄件人确实投了件——V2 的 signal 调用成功且发生在卡死之前

**代码佐证 1** `mf310p_v2_kernel.asc:65-71`（循环结构：**先发本块，后等前块**）：

```cpp
for (uint32_t k = 0; k < chunks; ++k) {
    ...MM(k)...                                    // 算第k块
    if (core == 0) {
        const bool ok = smem_shm_sdma_signal_at(reserved, ownC+start, peerDst+start,
                                                chunkBytes, kTagBase | k);  // ← 先发第k块的搬运请求
        CheckOrTrap(ok, status, 1);                // 失败会立刻Trap(阶段码不会是50)
    }
    if (k > 0) {                                   // overlap流水线
        wait(mail of chunk k-1);                   // ← 后等第k-1块的邮件
        Add(chunk k-1);
    }
}
wait(mail of chunk chunks-1);                      // 收尾等最后一块
```

**代码佐证 2** `smem_shm_aicore_base_sdma.h`（signal 原语——投件动作本身）：

```cpp
bool smem_shm_sdma_signal_at(res, src, dst, len, imm)
{
    // 满环等待后：
    *(volatile uint64_t*)(slot+0)  = src;          // 把4字段搬运请求写进"请求环"
    ... (dst/len/imm)
    DataCacheCleanAndInvalid(...);                 // 刷缓存，确保对端可见
    SdmaWriteCell(res, REQ_TAIL, tail + 1);        // 推进请求环尾游标 ← 投件完成
    return true;
}
```

**人话**：rank1 的核按协议在 k=0 一开始就把 chunk0 的搬运请求投进了**自家
快递站的取件槽**（请求环），投件成功（若失败核会当场 Trap 死在阶段 41/50
之前，而它活着走到了 50）。V2 侧的投递动作**有且只有这一步**——把 4 个数字
写进请求环。这一步成功了。

### 证据 ⑤：快递站接了单、出了库、下班了——控制面全绿，但货没到

**日志实值（停滞瞬间 `[MF_G1C]` / `[MF_DIAG]`，observed）**：

```
dev1 编排器: reqSeq: 8636  hwHead: 308 hwTail: 308 (队列空)  error: 0   phase: 8 (空闲)
dev0 编排器: reqSeq: 8634  hwHead: 302 hwTail: 302 (队列空)  error: 0   phase: 8 (空闲)
双设备 Epoch: 纪30/31 正常轮转，exitReason 全 0
```

**人话**：两侧 AICPU 快递站把请求环**全部消费完**（reqSeq 推到头）、硬件提交
队列**排空**、无任何错误码、按时打卡下班。控制面坚信"所有件都派完了"。

这正是执行计划从 G1-C 起反复敲黑板的那句话的实证：

> **"SQ 排空不能证明 SQE 正确落地"**（G1D_EXECUTION_PLAN §1）

**推理收口（derived）**：请求被投进环（证据④）→ 环被消费干净（证据⑤）→
但对应柜子从未出现新单（证据③）。丢失发生在**环消费之后、显存写入落地之前**——
这一段路全部在 MemFabric 的域内：AICPU 编排器的 SQE 组装/提交 → CP/SDMA
硬件执行 → 对端保留区写显存。

### 证据 ⑥：对面的卡死是"株连"——因果链只有一条，不是两起独立事故

把证据①④的循环结构代入两侧卡死位置（derived）：

| | rank0 | rank1 |
|---|---|---|
| 卡死在哪一步 | k=1 的 `wait(chunk 0)` | k=3 的 `wait(chunk 2)` |
| 死前已发出的 signal | chunk 0、1 | chunk 0、1、2、3（全部） |
| 它等的邮件由谁发 | rank1 的 `signal(chunk0)`——**已发**（k=0 时无条件先发） | rank0 的 `signal(chunk2)`——**永远不会发**（那要等 rank0 走到 k=2，但 rank0 卡死在 k=1） |

**人话**：rank1 等 chunk2 邮件是**注定等不到的**——寄件人 rank0 自己被卡在
更早的一步，根本没走到投递 chunk2 的动作。所以 dev1 环 442 号柜没有新单
**不需要任何额外解释**。

**全案只有一起原发性丢失：rank1→rank0 的 chunk0 邮件（单号 8633，dev0 环
440 号柜）。** 顺带解释了为什么两次故障（C2R2/D1R4）看起来"两方向各丢一封"：
其实是**一起单向丢失 + 对侧级联**，表象对称、因果单向。

## 五、直接回答：源头在 MemFabric 还是 V2？

**能判定，且证据指向明确：在 MemFabric 的发送落地链。**

置信度分层：

- **"不在 V2 融合算子实现代码"**：高置信。V2 侧每个环节都有直接的通过性证据，
  且对侧卡死有完整因果解释，无需假设任何 V2 缺陷。
- **"在 MemFabric 发送链（编排器 SQE 提交 → CP/SDMA 执行 → 落地）"**：高置信。
  丢失区间被两侧证据夹逼（证据④⑤在前、证据③在后），区间内只有 MemFabric
  的组件。
- **"是 MemFabric 的代码 bug 还是其配方踩中了硬件缺陷"**：**unknown**——
  软件取证的天花板。且 ~8632 次连续同型写入成功后才丢 1 次的画像，更像
  "特定时序条件下的硬件/协同边界问题"，而非确定性代码 bug。

仍缺的两块拼图（下次复现轮一步可得）：

1. **440 号柜隔壁（441/442 号）有没有被错投**——区分"写入彻底丢失"vs
   "写错槽位"。G1-D2 采样器（`[sha]`）读的是游标**后方**（已消费槽），
   应改为读游标**前方** head..head+4；
2. **每单回执**——AICPU 侧"我确实为第 N 号请求提交了 3 条 SQE"的逐单记录
   （涉及 SQE 配方区，按红线需专项评审才能加）。
